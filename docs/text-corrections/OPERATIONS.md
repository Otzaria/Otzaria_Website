# מערכת תיקוני הטקסט — מדריך תפעול

מסמך זה מיועד למפעילי האתר. החוזים עצמם: [`CONTRACT.md`](CONTRACT.md). הוראות למפתח שירות
הבדיקה החיצוני: [`VERIFY_SERVICE_GUIDE.md`](VERIFY_SERVICE_GUIDE.md).

## 1. מבט על

```
תוכנת אוצריא ──POST /api/reportingerrors──▶ ErrorReport (insert יחיד: דיווח + תור ידני / outbox, או email_only)
                                                 │
            worker (/api/cron/corrections-worker: מיד אחרי דיווח/אישור, ו-cron כל 10 דקות כרשת ביטחון)
                 ├─ outbox → CorrectionJob (verify / publish)
                 ├─ verify: resolver (GitHub, קריאה בלבד) → שירות הבדיקה → ניתוב לפי מדיניות
                 ├─ publish: PR מבודד או קומיט ישיר ליעד הקבוע בקוד → reconciliation → מעקב מיזוג
                 └─ heartbeat (WorkerHeartbeat)
מתנדבים ── /library/corrections ── /api/corrections/* (הרשאה נבדקת בשרת בכל פעולה)
```

האתר מתפקד כמערכת **ידנית מלאה** כששירות הבדיקה לא הוגדר מעולם: כל דיווח נכנס לתור הידני,
מתנדב מאשר, והפרסום (אם הוגדר) יוצא כ-PR.

**תקרות בקליטה.** נדחים (413/400, בלי חיתוך) רק השדות המדויקים של `correction` (20,000 כל אחד) וגוף
מעל 256KB. שדות התצוגה הישנים (`error_details`, `selected_text`, `context_text` וכו') נבדקים לטיפוס בלבד:
`error_details` נושא את בלוק ה-fallback של §2.5 (עד 2×20,000). הם נשמרים ונשלחים במייל מקוצצים לתצוגה,
כמו בלקוח ישן, וה-`content_digest` מחושב על מה שהתקבל — ההצעה המדויקת נשמרת רק מ-`correction`.

## 2. מצבים

המצב מפוצל לשדות נפרדים על מסמך הדיווח (לא enum יחיד):

| שדה | ערכים |
|---|---|
| `state` | `open`, `email_only`, `closed_published`, `closed_already_fixed`, `closed_rejected`, `closed_manual` |
| `verification.status` | `not_requested`, `queued`, `in_progress`, `completed`, `failed`, `superseded`, `skipped_service_disabled` |
| `approval.authority` / `approval.scope` | `none`/`service`/`volunteer` ו-`none`/`technical_only`/`technical_and_content` |
| `manual.status` | `none`, `queued`, `claimed`, `released` (+ `handoffReason`, `assignee`, `leaseExpiresAt`) |
| `publish.status` | `not_ready`, `ready`, `in_progress`, `unknown_needs_reconcile`, `pr_opened`, `committed`, `failed`, `skipped_already_fixed` |
| `inclusion.status` | `unknown`, `merged_to_main`, `included_in_release` |

- "אושר" אינו "פורסם": אישור מציב `publish.status=ready`. "PR נפתח" (`pr_opened`) אינו "מוזג";
  רק מיזוג שזוהה ע"י ה-worker מציב `committed` + `closed_published`. `merged_to_main` אינו "נכלל
  בגרסת ספרייה" — `included_in_release` אינו מוצב אוטומטית כלל.
- PR שנסגר בלי מיזוג (§4, "מעקב PR"): `pr_opened` עם `publish.prClosedAt` = ממתין שהתיקון ייקלט ב-main;
  התיקון נמצא שם → `committed` + `publish.absorbed=true` + `closed_published` (`closeReason=pr_absorbed`).
- כל מעבר הוא `findOneAndUpdate` יחיד עם תנאי `workflowGeneration` (ולפעולות worker — גם fence של
  המשימה). ה-generation עולה בכל מעבר שמפסיל עבודה ישנה: לקיחה, העברה לידני, עריכה, שליחה מחדש.
- השדה הישן `status` (`pending`/`in_progress`/`resolved`/`rejected`) ממשיך להתעדכן לתאימות.

## 3. הגדרות

ההגדרות מפוצלות לשלוש שכבות, ובכוונה:

### 3.1 מתגי התנהגות — מסך הניהול בלבד

דף **ניהול ובריאות** (`/library/corrections/admin`, מנהל כללי בלבד) שומר אותם במסמך
`SystemConfig` בשם `corrections.runtime` דרך `POST /api/corrections/admin/settings`:

| מתג | ברירת מחדל | משמעות |
|---|---|---|
| `intakeEnabled` | פעיל | קבלת דיווחים (כבוי → 503, התוכנה שומרת בתור שלה) |
| `publishMode` | `disabled` | `disabled` / `pr` / `direct` |
| `autoPublish` | כבוי | פרסום אוטומטי אחרי אישור מלא של השירות |
| `verifyPaused` | לא מושהה | השהיית שירות הבדיקה — הממתינים עוברים לידני |

`direct` כותב ישירות לענף בלי PR; המסך דורש אישור מפורש לפני המעבר אליו. `publishMode` שאינו
מהרשימה נדחה (400) ואינו נשמר; ערך פגום שכבר קיים במסמך נקרא כ-`disabled`.

### 3.2 env — סודות וכתובות בלבד

| משתנה | משמעות |
|---|---|
| `CRON_SECRET` | Bearer לכל `/api/cron/*`, כולל ה-worker |
| `DICTA_LIBRARY_GITHUB_TOKEN` | הטוקן היחיד לכתיבות GitHub של האתר: עריכת הספרייה, פרסום תיקונים, issues של דיווחי התוכנה. בלעדיו הפרסום כבוי (`publish_token_missing`) |
| `CORRECTIONS_VERIFY_ENABLED` + `_URL` + `_SECRET` | הפעלת שירות הבדיקה (כבוי כברירת מחדל) |
| `CORRECTIONS_VERIFY_AUTHORITY` | הסמכות שהאתר מעניק לשירות (`none`/`technical_only`/`technical_and_content`) |
| `CORRECTIONS_VERIFY_REQUESTED_SCOPE` | מה מבקשים מהשירות (לא יותר מהסמכות) |
| `CORRECTIONS_VERIFY_AUTO_REJECT` | האם `rejected` מהשירות סוגר אוטומטית |
| `CORRECTIONS_VERIFY_MOCK` | הכתובת היא שרת דמה (אסור בייצור) |

### 3.3 קבוע בקוד (`src/lib/corrections/config.js`)

יעד הפרסום והמקור הם `Otzaria/otzaria-library@main` — אותו ריפו וענף לקריאה ולכתיבה. גם כל
הכוונון קבוע ומיוצא כקבועים: `VERIFY_MAX_ATTEMPTS` (6), `VERIFY_MAX_TOTAL_SECONDS` (86400),
`VERIFY_TIMEOUT_MS` (20000), `VERIFY_BACKOFF_BASE_SECONDS` (30) ו-`_CAP_SECONDS` (3600),
`PUBLISH_MAX_REF_RETRIES` (3), `PUBLISH_MAX_ATTEMPTS` (5), `PR_ABSORPTION_GRACE_SECONDS` (14 יום),
`PR_ABSORPTION_RELOCATION_LINES` (50), `PR_REJECTED_LABELS` (`לא נקלט`, `rejected`, `wontfix`, `invalid`),
`PR_ABSORPTION_CACHE_BYTES` (32MB), `WORKER_BATCH_SIZE` (10),
`WORKER_CONCURRENCY` (2), `JOB_LEASE_SECONDS` (120), `HEARTBEAT_STALE_SECONDS` (300),
`MANUAL_CLAIM_MINUTES` (24 שעות), `SOURCE_CACHE_BYTES` (64MB), `SOURCE_HEAD_TTL_SECONDS` (30),
`DIFF_CONTEXT_LINES` (3 — "הרחב הקשר" בתצוגת המתנדב מוסיף עד 50). שינוי דורש שינוי קוד.

כללי בטיחות שנאכפים בקוד (`config.js`):

- בייצור (`NODE_ENV=production`): `CORRECTIONS_VERIFY_MOCK=1` משבית את השירות, מאפס את הסמכות
  ל-`none` ומכבה פרסום ודחייה אוטומטיים; כתובת `http://` או `localhost` נדחית.
- חוסר בסוד/כתובת/הגדרה = השירות כבוי עם סיבה מפורשת → כל דיווח לידני, בלי ניסיונות.
- יעד הפרסום אינו מגיע לעולם מהבקשה, מהתוכנה או מהשירות. הנתיב בקובץ נבדק מול שורשי הספרים
  (`isAllowedRepoPath`) — אין כתיבה ל-`.github/` או מחוץ ל-`<מקור>/ספרים/אוצריא/`.

## 4. ה-worker

### מתי הוא רץ

עבודה חדשה מריצה אצווה **מיד בסיום הבקשה שיצרה אותה**, דרך `after()` של Next: קליטת דיווח
שנכנס למערכת (לא `email_only`), ואישור/עריכה-ואישור/שליחה-מחדש של מתנדב. ההרצה best-effort —
כשל בה נרשם ללוג ואינו מכשיל את הבקשה. שתי אצוות אינן יכולות לרוץ במקביל באותו תהליך:
הכל עובר דרך `runBatchOnce()` ב-`src/lib/corrections/run-batch.js`.

התזמון הוא **רשת ביטחון בלבד** — ניסיונות חוזרים אחרי כשל, lease שפג, והמתנה לתשובת שירות
הבדיקה. מספיקה הרצה אחת כל 10 דקות:

```
*/10 * * * * curl -fsS -X POST -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron/corrections-worker >> /var/log/corrections-worker.log 2>&1
```

**בייצור ה-cron הזה אינו מותקן** (נבדק ב-2026-11-25: ב-crontab של השרת אין קריאה ל-`corrections-worker`),
ולכן אצוות רצות רק מתוך בקשות — כשנכנס דיווח או כשמתנדב מאשר. מומלץ להתקין אותו: בלעדיו ניסיונות
חוזרים, זיהוי PR שמוזגו ובדיקה חוזרת של PR שנסגרו וממתינים לקליטה ב-main מתעכבים עד הבקשה הבאה.

`scripts/corrections-worker.mjs` נשאר בריפו להרצה ידנית ולפיתוח (`--once` מריץ אצווה אחת
ויוצא). אין צורך בשירות pm2/systemd קבוע. משתני הסקריפט: `CRON_SECRET`, `CORRECTIONS_WORKER_URL`
(ברירת מחדל `http://127.0.0.1:3000`), `CORRECTIONS_WORKER_ID`; הוא נטען מ-`.env` אם קיים.

- **עמידות**: כל המצב ב-MongoDB. אין `setTimeout`/זיכרון/Promise אחרי תשובה. restart של האתר
  לא מאבד עבודה.
- **תפיסה**: `findOneAndUpdate` אטומי; lease (`JOB_LEASE_SECONDS`, 120; פרסום ×5)
  עם fence שעולה בכל תפיסה. worker שה-lease שלו פג ומנסה לסיים — נכשל בשקט.
- **משימה פעילה יחידה** לכל פעולה/דיווח: אינדקס ייחודי על `activeKey`.
- **מקביליות**: `WORKER_BATCH_SIZE` (10) משימות לאצווה, `WORKER_CONCURRENCY` (2) במקביל;
  אותו תהליך לא מריץ שתי אצוות במקביל. כמה תהליכים/שרתים במקביל — בטוח.
- **שבת/יו"ט**: ה-worker מושהה תמיד (דופק נרשם עם `paused: shabbat`), גם בהרצה שנוצרה מבקשה.

### Retries (שירות הבדיקה)

המסווג היחיד `classifyVerifyFailure` (`classify.js`):

| סיווג | מקרים | פעולה |
|---|---|---|
| transient | timeout, ECONNRESET/ECONNREFUSED/EAI_AGAIN, 408/429/500/502/503/504, `service_capacity` | backoff מעריכי עם jitter; `Retry-After` מכובד עד התקרה |
| permanent | כבוי/לא מוגדר/חסר סוד, 400/401/403/404/405/410/422, ENOTFOUND, TLS, JSON פגום, שדות חסרים, מזהים לא תואמים, api_version לא נתמך | ידני מיד |
| unknown | כל השאר (כולל 3xx — הפניות נחסמות) | ידני מיד |

גבולות (קבועים ב-`config.js`): `VERIFY_MAX_ATTEMPTS` (6), `VERIFY_MAX_TOTAL_SECONDS` (86400),
`VERIFY_BACKOFF_BASE_SECONDS` (30), `_CAP_SECONDS` (3600), `VERIFY_TIMEOUT_MS` (20000).
מיצוי → ידני עם `retries_exhausted` / `deadline_exhausted`. `request_id` זהה בכל ניסיון חוזר; חדש רק בשליחה
מחודשת מפורשת. תשובת 202 = polling לכתובת הבסיס שבהגדרה בלבד (לעולם לא לכתובת מהתשובה).

תשובה מאוחרת (מתנדב לקח בינתיים / generation השתנה) נשמרת ב-`decisions` עם `stale:true` וביומן —
ולא מקדמת מצב.

### פרסום

1. קריאת ראש הענף + ה-blob מאותו קומיט.
2. הקובץ זהה ל-blob של החבילה (`base_blob_sha`): אימות שהשורה ב-`line_index` היא בדיוק `original_line` (אחרת: אם
   היא כבר `new_line` → `skipped_already_fixed` בלי קומיט; אחרת → האישור נפסל, הדיווח חוזר לידני עם
   `source_changed_after_approval`).
   הקובץ **השתנה** מאז הבסיס: מקום הכתיבה נקבע רק באיתור (`locateTarget` ב-`locate-edit.js`, מול הבסיס שנקרא לפי
   `base_blob_sha`) — לעולם לא לפי האינדקס לבדו, כי באינדקס הישן עלולה לעמוד שורה זהה מפסקה אחרת (או ההצעה עצמה
   בפסקה אחרת) כשהפסקה המדווחת זזה ועדיין שגויה. `skipped_already_fixed` רק כשהאיתור קובע `fixed`; כתיבה רק כשהפסקה
   המדווחת לא תוקנה והיא המופע היחיד בקובץ — של המקור, של פסקה דומה ושל חתימות הטעות — ובבסיס לא היה לה תאום;
   הכתיבה בשורה שאותרה (גם אם זזה). כל השאר → התנגשות: האישור נפסל והדיווח חוזר לידני (`source_changed_after_approval`),
   עם `publish.conflictReason` — `source_changed` כשבאינדקס נוסח אחר, `source_not_resolved` כשבאינדקס עדיין המקור או
   ההצעה אבל הפסקה לא אותרה בוודאות. המחיר: אחרי שינוי בקובץ, שורה שחוזרת בספר (למשל כותרת זהה בכמה מקומות) עוברת
   לאישור מחדש במקום להיכתב באינדקס.
   האיתור מנורמל (בלי תגיות) ומזהה רק את הפסקה, ולכן `skipped_already_fixed` אחרי שינוי בקובץ דורש גם שכל השינוי
   **הגולמי** שאושר נמצא (הביקורת הרביעית): הפסקה שאותרה היא שורה אחת, ובה ההצעה עצמה או העריכה הגולמית בהקשרה
   (אותה ראיה כמו ב"נקלט", `editState`); ואין בשום מקום בקובץ עותק שבו המילה תוקנה ושינוי התגיות לא (`rawPartHeld`,
   כלל 8 למטה). תיקון שנקלט בחלקו (המילה בלי שינוי ה-HTML, או להפך) או פסקה שפוצלה לכמה שורות → התנגשות
   `source_changed` → ידני.
3. תוכן חדש עם שימור BOM, סיומת השורה של כל שורה ושאר הקובץ בייט-לבייט.
4. blob → tree (base = אותו head) → commit (parent = אותו head).
5. `pr`: ענף `corrections/<report-id>-<publish-attempt-id>` + PR. `direct`: `PATCH refs` עם `force:false`.
6. 422 (הענף התקדם) → חוזרים ל-1 (עד `PUBLISH_MAX_REF_RETRIES`). שינוי לא קשור באותו קובץ
   נשמר; תוכן מבסיס ישן לעולם לא משולב עם parent חדש.

הודעת הקומיט: `תיקון: <ספר> — <מיקום>` + `Report-Id:` + `Publish-Attempt:`. אין אימייל, נתיב מקומי או
הסבר המשתמש בקומיט/PR (כתובות מייל ונתיבי דיסק מסוננים מהכותרת).

**תוצאה לא ידועה** (נפילה אחרי כתיבה ל-GitHub ולפני עדכון ה-DB, או שגיאת רשת באמצע): הניסיון נשאר
`started`/`unknown`. לפני כל ניסיון נוסף ה-worker מבצע reconciliation — מחפש את `Publish-Attempt` בענף
ה-PR או ב-50 הקומיטים האחרונים שנגעו בקובץ — ורק אם לא נמצא, כותב מחדש.

**מעקב PR**: בכל אצווה נבדקים עד 10 PR פתוחים ועד 10 PR שנסגרו וממתינים לקליטה — כל קבוצה בתור משלה,
הוותיקים בבדיקה קודם. מוזג → `committed`/`closed_published`; בסיס השתנה בזמן שה-PR פתוח →
`publish.conflictReason=base_changed_while_pr_open` (תווית "התנגשות"); PR שנפתח מחדש חוזר למעקב הרגיל.
כש-GitHub כבר החזיר את ה-PR פתוח, כשל בבדיקת המקור הנוספת (סימון ההתנגשות; למשל 503) אינו מעביר לידני: ההמתנה
מתאפסת, הסימון הקודם נשאר והשגיאה נרשמת (`pr_source_check_failed:<status>`). האיפוס מותנה במצב שנקרא (הביקורת החמישית).

**PR שנסגר בלי מיזוג אינו "נדחה"**: מנהל הספרייה בודק כל PR, מחיל אותו בקומיט מקומי מרוכז שנדחף ל-main
מאוחר יותר, וסוגר את ה-PR בלי מיזוג (בהערה כמו "נקלט בקומיט מקומי" או "כבר קיים בעץ"). לכן ה-worker קורא
את הקובץ ב-`Otzaria/otzaria-library@main` (קריאה בלבד; ראש הענף נקרא פעם אחת לאצווה) ומשווה אותו לחבילת
השינוי (`absorption.js`, `closed-pr.js`):

1. **איתור שורת היעד (עיגון)**: המקום ב-main שבו השכנים של השורה — עד שתי שורות לא-ריקות מכל צד, כפי שהיו
   בבסיס בזמן האישור — תואמים (כולם, או כולם חוץ מאחד כשידועים שלושה ומעלה), עד 50 שורות מהמיקום המקורי
   (`PR_ABSORPTION_RELOCATION_LINES`). הבסיס: ההקשר שנשמר באישור (`resolvedSource.context`), ואם הוא חלש —
   ה-blob של הבסיס מהחבילה, או (דיווח בלי חבילה) הקובץ בהורה של קומיט ה-PR. שורה ארוכה ששכן שלה נערך גם הוא
   (רוב המילים משותפות) עדיין "אותה שורה"; שורה קצרה — רק בהתאמה מדויקת.
2. **הבדיקה רק בשורה המעוגנת**: השורה כולה זהה להצעה או למקור, או — כשהוחלו באותה שורה ארוכה גם תיקונים
   אחרים — העריכה של הדיווח בהקשרה. מופע של הנוסח המתוקן בשורה אחרת אינו ראיה (ייתכן שהיה שם כבר בבסיס).
3. **בלי עיגון** (השכנים לא נמצאו — למשל מנהל הספרייה פיצל או איחד פסקאות — או נמצאו בכמה מקומות): "נקלט"
   רק כשהמקור (השורה או העריכה) אינו נמצא עד 50 שורות מהמיקום המקורי, ועם הקובץ המלא בבסיס — רק כשמספר
   השורות שנושאות את התיקון בסביבה גדל בדיוק באחת לעומת הבסיס (מופע שהיה שם כבר אינו ראיה, גם אם זז או נערך).
   הספירה היא של **מופעים** (לא שורות): פיצול פסקה ליד העריכה אינו מוסיף מופע. **כשהבסיס המלא אינו זמין
   (לא נקרא, אינו תואם, או שגיאה) — כל "נקלט", מעוגן או לא, הופך ל-`changed` (`base_required`): ממתין, נבדק שוב
   במחזור הבא ובתום ההמתנה לידני; הוא לעולם אינו נסגר כפורסם.**
4. **המקור בשום מקום בקובץ (כלל גרסה 5, `ABSORPTION_RULE_VERSION`)**: "נקלט" דורש שהשורה המקורית או דפוס העריכה
   המקורי (באותו נרמול: NFC ורווחים) לא יופיעו **בשום מקום בקובץ כולו** — לא רק בחלון 50 השורות. פסקה מקורית
   שזזה רחוק ונשארה שלמה פירושה שהשגיאה עדיין בספר, גם אם נוסח מתוקן אחר קיים בקובץ: התוצאה `pending`
   (`original_elsewhere`) → ממתין ובתום ההמתנה ידני. תוצאה מוכרת ומקובלת: עותק כפול של הפסקה שנשארה בו השגיאה
   (כמו בקובץ של PR #299) או כותרת זהה במקום אחר מעבירים לידני במקום לסגור כפורסם.
5. **ראיה חדשה גם בנתיב המעוגן**: כשהבסיס המלא ידוע, בקובץ כולו מספר מופעי התיקון חייב לעלות לעומת הבסיס
   (`fix_not_new` אחרת). כך עותק כפול של הפסקה, שכבר נשא את התיקון בבסיס והעיגון ננעל עליו, אינו ראיה.
   כשהבסיס אינו נקרא, גם "נקלט" מעוגן הופך ל-`changed` (`base_required`) — העיגון לבדו אינו ראיה (עותק כפול), והבדיקה החוזרת תתבצע במחזור הבא.

6. **איתור הפסקה המדווחת (כלל גרסה 6, `ABSORPTION_RULE_VERSION`; `src/lib/corrections/locate-edit.js`)**: כל "נקלט",
   בכל נתיב, מותנה גם בכך ש(א) הפסקה המדווחת **מזוהה בקובץ בביטחון** — גם אחרי הזזה, עריכות במקום אחר בה, פיצול
   או איחוד עם שורות סמוכות — ו(ב) **בתוך הפסקה, במקום שהעריכה ממופה אליו**, המקור איננו וההצעה ישנה. הבדיקות
   1–5 נשארות כתנאים שמרניים נוספים. אותו מודול ישמש את כללי "כבר תוקן".
   - **נרמול** אחד לבסיס, להצעה ולקובץ: BOM, צורות הצגה (U+FB1D–FB4F, למשל U+FB33), NFC, הסרת תגיות (`<br>` → רווח)
     ורווחים. עריכה שאינה נראית אחרי הנרמול (תגיות/רווחים בלבד) — ספק.
   - **זיהוי**: המילים של שורת הבסיס *מחוץ* לעריכה מיושרות (LCS, אותם צ'אנקים כמו במיזוג השורות ב-`rebase-change.js`)
     מול כל שורה וכל חלון של 2–3 שורות לא-ריקות סמוכות, אחרי סינון באינדקס מילים. הציון הוא Dice על המילים
     (פיסוק אינו מזהה פסקה), בלי טווח העריכה — עותק מתוקן ועותק שלא תוקן מקבלים אותו ציון. "דומה" = ציון ≥ 0.5;
     הדומה המזוהה חייב ≥ 0.75 (או ≥ 0.5 כשהשכנים מהבסיס מאשרים את מקומו) ופער ≥ 0.2 מהדומה הבא.
   - **מיפוי**: שני אסימונים צמודים מכל צד של העריכה חייבים להופיע ללא שינוי (בקצה הפסקה — גבול שורה). בין
     העוגנים: ההצעה → `fixed`; המקור → `not_fixed`; טקסט אחר או עוגן שהשתנה (מילים שנערכו ליד הטעות) → `uncertain`.
   - **`fixed` רק כש** כל הדומים בקובץ מתוקנים (כולל כמה עותקים שאוחדו לשורה אחת); נשאר דומה מתוקן מעבר לתאומים
     המתוקנים שכבר היו בבסיס (עותק שנשאר זהה אינו ראיה ואינו מתחרה בזיהוי); והזיהוי חד-משמעי. שורה קצרה (פחות מ-4
     אסימונים מחוץ לעריכה, למשל כותרת): רק התאמה מלאה של השורה במקום שהשכנים מהבסיס מאשרים, ובלי שום שורה
     שמכילה את המקור (כולו, או עם צד אחד של ההקשר). מחיקת תוכן השורה כולה אינה ניתנת לזיהוי — תמיד ידני.
   - **הטעות בשום מקום, גם מעבר לגבולות שורות (כלל גרסה 7)**: `fixed` דורש גם שחתימות הטעות לא יופיעו בשום מקום
     בזרם האסימונים של הקובץ כולו (בלי גבולות שורות). חתימה = אסימוני המקור במקום העריכה עם הקשר מצד אחד (בהוספה —
     משני הצדדים; בקצה השורה — בתנאי שאחריה/לפניה אין את ההוספה), באורך הקצר ביותר שבבסיס מופיע רק בשורת הדיווח
     ושאינו מופיע בהצעה; בשורה ארוכה לפחות אסימון הקשר אחד, בשורה קצרה גם הצ'אנק לבדו. אין אורך כזה (למשל תאום זהה
     בבסיס) → הקצר ביותר, וכל מופע שלו חוסם. כך מקור שזז ופוצל לכמה שורות, אוחד עם שכנה או הורחב — גם כשבמקומו הישן
     עומד עותק זהה להצעה — נשאר `uncertain` (`original_fragment`). קודם החיפוש היה בשורה או בחלון של עד 3 שורות,
     ובשורה קצרה רק בשורות באורך דומה — ושני מקרי הביקורת על #312 (כותרת שפוצלה לארבע שורות, כותרת שהורחבה) נסגרו
     בטעות כ-`closed_published`.
   - **שינוי התגיות שאושר (כלל גרסה 8, הביקורת הרביעית; `rawPartHeld` ב-`absorption.js`)**: האיתור אינו רואה
     תגיות, ולכן "נקלט" (וגם "כבר תוקן" במפרסם) דורש שבשום מקום בקובץ אין עותק שבו המילה תוקנה ושינוי התגיות לא.
     לכל צ'אנק גולמי (תגית שלמה = אסימון) שמשנה תגיות: קטע מעיד — המקור כפי שהוא (צ'אנק של תגיות בלבד), או הטקסט
     החדש בתוך התגיות הישנות (צ'אנק שמשנה גם טקסט) — עם הקשר עד מילה שלמה מכל צד. חוסם כשבקובץ יש ממנו יותר מופעים
     ממה שהיה אחרי קליטה מלאה (בבסיס, פחות שורת המקור, ועוד ההצעה) — גם כשבמקום שאותר עומדת שורה זהה להצעה (פיתיון
     במקום הישן, תאום תקין מהבסיס). אי אפשר לחשב (שורה ענקית עם שינוי תגיות, תגיות באמצע טקסט שהשתנה) → חוסם.
     → `changed` (`raw_part_not_applied`). שינוי בלי תגיות — ללא שינוי.
   - **כלל גרסה 9 (הביקורת החמישית)** מחליף את הקטעים המעידים: הקטע הגולמי הרציף לא נמצא בעותק שבו נשארה התגית שהוסרה
     אבל עם תגית זרה בתוכה (`<b><i>…</i></b>`) או בתגית שקולה (`<strong>`), והשורה הזהה להצעה במקום הישן נחשבה ראיה.
     עכשיו לכל צ'אנק שמשנה תגיות יש חלונות של אסימוני ההצעה: סביבו (מילה מכל צד), ומילים משמאל או מימין לבד, או
     האסימונים שבתוך הצ'אנק — לעותק שפוצל או נערך ליד השינוי (גם המילה שבתוך התגית). חלון חלקי נבחר רק כשהוא מזהה את
     הפסקה: הקצר ביותר שאינו מופיע בבסיס מחוץ לעותקי הפסקה (בלי בסיס — שתי מילים לפחות). כל מופע של חלון בשורה שנכתבה
     מאז הבסיס (או בשורה זהה למקור) חייב לשאת בדיוק את התגיות שבהצעה; כל סטייה — התגית הישנה, תגית שקולה או זרה,
     פיצול לשורות בתוך החלון — חוסמת. שורה שלא השתנתה מהבסיס אינה נספרת (אין ספירה יחסית שתיקון במקום אחר יקזז).
     המחיר: עותק שזז ועוצב מעט אחרת ליד השינוי עובר לידני (במחולל בלי עיצוב מחדש — כ-1.5% מהסגירות של הצעות עם
     תגיות). עותק שנגרס כך שהמילה שבתגית נותקה מכל שכניה המקוריים אינו ניתן לייחוס — כמו בטקסט.
   - **התוצאה**: `not_fixed` → `pending` (`original_located`); ספק → `changed` (`unlocated_<סיבה>`, למשל
     `lookalike_unresolved`, `ambiguous`, `not_identified`, `fix_not_new`, `original_fragment`, `crowded_*`) — ממתין
     ובתום ההמתנה ידני.
   - **ביצועים**: אינדקס לכל קובץ (שורה מנורמלת → מקומות, מילה → שורות, אסימונים) ואינדקס סריקה לבדיקות 4–5 נבנים
     פעם אחת לכל עותק שורות ומשותפים לכל הדיווחים על אותו קובץ באצווה; עותקי הבסיס המפורקים נשמרים במטמון המוגבל
     (`PR_ABSORPTION_CACHE_BYTES`), לא במפה שגדלה לאורך ההרצה.
   - **בדיקת תכונה** (`locate-edit.test.mjs`, 3,000 תרחישים עם seed קבוע בכל הרצה; `LOCATE_PROPERTY_SCENARIOS` להרצה
     עמוקה): הזזה קרובה/רחוקה, עריכת מילים ליד/רחוק מהטעות, שורות שכבר נושאות את ההצעה, תאומים ושכפול מתוקן/לא,
     פיצול ואיחוד, ותיקון במקום הנכון, בחלק מהעותקים, במקום הלא נכון או בכלל לא. האינווריאנט: נסגר ⇒ הטעות בפסקה
     המדווחת (בכל עותקיה) תוקנה. הקוד שלפני הכלל נכשל בו (עשרות סגירות שגויות ב-3,000 תרחישים); הכלל עבר גם
     הרצה עמוקה של 200,000 תרחישים בלי הפרה.
   - **בדיקת תכונה נוספת (הביקורת, כלל 7)**: אותו מחולל עם `reshape` — הזזה עם פיצול ל-k שורות, איחוד עם שכנה או
     הרחבה בשורה (גם מילה צמודה לטעות), פיתיון זהה להצעה במקום הישן ופיתיון זהה למקור במקום אחר. "פתוח" = מקום טעות
     שלא תוקן ועדיין צמוד בזרם לשכן מקורי (מילה כפולה — לבת-זוגה); מקום שנותק מכל שכניו (הפסקה נחתכה סביבו והחלקים
     פוזרו) אינו ניתן לייחוס בשום טקסט ונספר בנפרד. נבדק גם `locateTarget`: יעד ⇒ הכתיבה בו מתקנת את הטעות בכל עותקי
     הפסקה. 3,000 תרחישים בכל הרצה: 0 הפרות (הקוד שלפני כלל 7 — 3). הרצה עמוקה של 200,000: 0 הפרות בשני המחוללים
     (הקוד הקודם — 170 סגירות שגויות במחולל החדש) ו-0 כתיבות שגויות; שיעור הזיהוי במחולל הרגיל 55.4% → 54.6%
     (קליטה 46.5% → 45.8%). 34 תרחישים (0.02%) שבהם מילת הטעות נותקה מכל שכניה ופוזרה — נסגרים.

**מגבלה ידועה (C3) — נסגרה בכלל 6**: שורה חדשה שנוספה מיד מעל היעד ונושאת את נוסח התיקון, כשביעד עצמו הוחל תיקון
אחר בתוך 12 תווי ההקשר והשגיאה נשארה — הפסקה המדווחת עדיין "דומה" ובה המיפוי סביב הטעות אינו ודאי, ולכן ספק ולא
"נקלט". המחיר הידוע של כלל 6: עותק זהה שלא תוקן במקום אחר בקובץ, פסקה קצרה שזזה, עריכה צמודה לטעות או כמה עותקים
מתוקנים חדשים — עוברים לידני בתום ההמתנה במקום להיסגר אוטומטית. כלל 7 מוסיף: מופע של חתימת הטעות בכל מקום בקובץ
(גם טקסט חדש שבמקרה נושא אותה) חוסם "נקלט".

  PR) — האצווה מעבירה לידני דיווחים שתמה המתנתם. PR שהוחזר 404 נבדק כמו PR שנסגר.
- **הערת הסגירה של מנהל הספרייה** (ההערה האחרונה עד הסגירה, מקוצרת ובלי כתובות מייל) נשמרת ב-`publish.prCloseComment`
  ומוצגת בדף הדיווח ובהיסטוריה — להצגה בלבד: המערכת לעולם אינה מנתחת את הטקסט כדי להחליט.
- **מוסכמה עם מנהל הספרייה**: PR שנסגר ולא נקלט — לסמן בתווית `לא נקלט` (או `rejected` / `wontfix` / `invalid`)
  לפני הסגירה או אחריה. הדיווח יחזור לטיפול מיד, בלי 14 יום המתנה. תווית לעולם אינה סוגרת דיווח כפורסם —
  רק בדיקת התוכן ב-main. בלי תווית — ההתנהגות הרגילה.
- **יעילות**: כל PR, הערותיו וכל קובץ נקראים פעם אחת לאצווה, וכל קובץ מפורק פעם אחת. דיווח ממתין אינו נבדק
  שוב כש-main לא זז, או כשה-blob של הקובץ לא השתנה (`publish.absorptionCheck`: sha של main ושל הקובץ, התוצאה
  ומועד הבדיקה). הקבצים נשמרים במטמון נפרד (`PR_ABSORPTION_CACHE_BYTES`), כך שקבצים ענקיים אינם דוחקים את
  מטמון התצוגה והפרסום.
- דחייה באתר אחרי אישור סוגרת את הדיווח לפני שהיא סוגרת את ה-PR, ולכן אינה עוברת בדיקה זו; דחיית דיווח
  שממתין לקליטה רק מוסיפה את הסיבה כהערה ב-PR שכבר נסגר. PR חדש (אישור מחדש) מאפס את שדות ההמתנה.
- כל המעברים: `findOneAndUpdate` יחיד, מותנה ב-`workflowGeneration`, במצב הפרסום, במספר ה-PR ובסימון ההמתנה
  `publish.prClosedAt` כפי שנקרא: בזיהוי הסגירה הראשון — שהוא עדיין ריק (שתי אצוות מקבילות — רק אחת רושמת); בהמתנה —
  שהוא אותו מועד. אצווה שראתה שה-PR נפתח מחדש מאפסת אותו, ולכן אצווה ישנה שהחליטה שההמתנה תמה אינה מעבירה לידני
  (ומשם PR שני לאותו תיקון) ואינה מחזירה את ההמתנה (הביקורת הרביעית).

## 5. בריאות

`GET /api/corrections/admin/health` (מנהל ספרים/כללי) ודף **ניהול ובריאות**:
דופק אחרון, גיל המשימה הוותיקה (בדיקה/פרסום), ספירות, ותיאור ההגדרות בלי סודות. `runtimeSwitches`
בתשובה מציין אילו מתגים מגיעים ממסך הניהול ולא מ-env.
בספירות, `prOpened` הם PR פתוחים ו-`prClosedAwaiting` הם PR שנסגרו וממתינים לקליטה. רק הראשונים נחשבים "עבודה
ממתינה" ל-`worker_not_running`: ההמתנה לקליטה נמשכת ימים בכוונה, עם cron או בלעדיו.
`healthy=false` כאשר: אין דופק טרי (`HEARTBEAT_STALE_SECONDS`, 300) ויש עבודה ממתינה; האצווה
האחרונה נכשלה; יש פרסום בתוצאה לא ידועה; יש שגיאות הגדרה.

| `publish_unknown_pending` | בדרך כלל נפתר לבד באצווה הבאה (reconciliation). אם GitHub לא זמין — ממתין; אין לפרסם ידנית בינתיים |

| `source_changed_after_pr_close` | השורה ב-main שונתה אחרת עד תום ההמתנה: להשוות את הנוסח הנוכחי להצעה (לרוב הוחל בשינוי קל) ולסגור, או לאשר מחדש |
| `pr_rejected_by_maintainer` | מנהל הספרייה סימן את ה-PR בתווית דחייה: לקרוא את הערתו ולהחליט — לא לאשר שוב כמו שהוא |
| `pr_closed_unverified` | לא הייתה בדיקה מוצלחת של main עד תום ההמתנה (קובץ ענק, תקלה קבועה, פרסום כבוי): לבדוק ידנית |

| מתנדב חדש | דף **ניהול ובריאות** → מתנדבי תיקונים → סימון "מתנדב" (מנהל ספרים/כללי). ההרשאה אינה נותנת גישה לפאנל הניהול |

## 7. דיווחים שאינם נכנסים למערכת (`email_only`)

הזכאות נקבעת לפי ניתוב המייל הקיים (`getEmailRecipients` ב-`report-email.js`, דרך `reachesOtzariaInbox`)
ולפי אותו `source_folder` (CONTRACT §1.4):

- המייל מגיע לתיבת אוצריא (ראשי או עותק) → הדיווח נכנס למערכת; המייל למקור (אם יש) ממשיך במקביל.
- המייל לא מגיע לאוצריא (היום: `source_folder` שמכיל `sefaria`, בלי תלות ברישיות) → `state=email_only`:
  נשמר ונשלח במייל בדיוק כמו קודם, בלי תור ידני, בלי בדיקה ובלי פרסום. מופיע רק בלשונית "הכל".
- שינוי נמעני המייל ב-`getEmailRecipients` משנה אוטומטית גם את הזכאות. דיווחים ישנים שעוד לא עברו
  migration ממופים לפי אותו כלל (`NON_OTZARIA_SOURCE_FOLDER_RE` — חייב להישאר תואם, מכוסה בבדיקה).

## 8. Rollout

1. **אתר חדש, ידני** — לפרוס; להריץ `node scripts/migrate-corrections.mjs` (dry-run) ואז `--apply`.
   השירות כבוי, `publishMode=disabled`. לקוחות ישנים ממשיכים לעבוד (200, `duplicate`, `reportId`, `savedToDatabase`).
2. **worker** — להגדיר `CRON_SECRET` ולהוסיף cron כל 10 דקות. לוודא דופק בדף הבריאות.
   להגדיר `DICTA_LIBRARY_GITHUB_TOKEN` ולבחור `publishMode=pr` במסך הניהול כדי שאישורי מתנדבים ייצאו כ-PR.
3. **גרסת תוכנה** עם `schema_version: 2` — ההצעות המובנות מופיעות בממשק.
4. **חיבור השירות** — `CORRECTIONS_VERIFY_ENABLED/URL/SECRET`, סמכות `technical_only`. כל אישור עדיין עובר למתנדב.
5. **אוטומציה** — רק אחרי תקופת מעקב: `CORRECTIONS_VERIFY_AUTHORITY=technical_and_content`,
   `CORRECTIONS_VERIFY_REQUESTED_SCOPE=technical_and_content`, ו"פרסום אוטומטי" במסך הניהול (עדיין PR).

שלבים 1–3 שימושיים בלי 4–5.

### PR שנסגרו בלי מיזוג (migration חד-פעמית)

לפני התיקון, מעקב ה-PR העביר כל PR שנסגר בלי מיזוג לתור הידני (`publish_failed`, `publish.lastError=pr_closed_unmerged`),
גם כשהתיקון כבר נקלט ב-main. אחרי הפריסה, להריץ בתיקיית האתר בשרת:

```sh
node scripts/migrate-corrections-closed-prs.mjs --out /tmp/closed-prs-dry.jsonl   # dry-run: ספירות + שורה לכל דיווח
node scripts/migrate-corrections-closed-prs.mjs --apply --out /tmp/closed-prs-apply.jsonl
node scripts/migrate-corrections-closed-prs.mjs --revert            # ביטול (dry-run); לביצוע: --revert --apply
```

הסקריפט מעריך מחדש, באותו כלל של ה-worker, כל דיווח פתוח שנכשל עם `pr_closed_unmerged` (גם כאלה שה-worker
החדש העביר לידני מאותה סיבה). ההמתנה נספרת מזיהוי הסגירה (`publish.updatedAt` של הכשל), ולכן דיווח שה-PR
שלו נסגר לפני יותר מ-14 יום והתיקון עדיין לא ב-main נשאר ידני (עם הסיבה המפורשת). תוויות הדחייה נקראות
בקריאה אחת לכל תווית; הערת הסגירה נשמרת לדיווחים שנשארים פתוחים. בדיווח שמתנדב מטפל בו כעת (שיוך בתוקף)
לא נוגעים (`skippedClaimed`), גם אם נלקח באמצע ההרצה (התנאי נבדק בכתיבה). כשמצב הפרסום כבוי — דיווחים שהיו
עוברים להמתנה נשארים בתור (`skipped.awaitPublishDisabled`), כי מעקב ה-PR לא יבדוק אותם.

כל הדיווחים מושווים לאותו קומיט של main (`mainSha`), וכל קובץ נקרא מ-GitHub פעם אחת (`files`, `githubRequests`;
עם ניסיון חוזר לתקלה זמנית). בפלט: `outcomes` (absorbed / pending / changed), `details`, `anchored`, `actions`
(`close_absorbed`, `await`, `handoff_*`) ו-`written`. `--out`: שורת JSON לכל דיווח (מזהה, PR, נתיב, שורה, תוצאה,
פעולה, מועד תום ההמתנה) — בלי תוכן ובלי פרטים אישיים. קוד יציאה 1 כשהיו שגיאות — הרצה חוזרת משלימה אותן.
הרצה חוזרת בטוחה: דיווח שכבר בתור הידני עם אותה סיבה אינו נכתב שוב (`unchanged`), ודיווח שהתיקון שלו הגיע
ל-main בינתיים נסגר.

**ביטול**: כל מעבר נרשם ביומן עם `actorKind=system`, `data.migration=true` ו-`data.before` (המצב שלפניו).
`--revert --apply` מחזיר כל דיווח שלא השתנה מאז (אותו `workflowGeneration` כמו באירוע ה-migration האחרון שלו)
למצב שלפני השרשרת הרציפה של מעברי ה-migration שלו, ומוחק את שדות ההמתנה. דיווח שמעקב ה-PR, מתנדב או כל
פעולה אחרת שינו אחרי ה-migration — אינו מבוטל (`skippedChanged`). אידמפוטנטי; ביומן: `migration_reverted`.
ה-snapshot אינו שומר לוקח ותפוגה, ולכן דיווח שמצבו הקודם היה "נלקח" (לקיחה שפגה) חוזר לתור הידני **לא נלקח**
(`manual.status=queued`, שדות הלקיחה מנוקים, `status=pending`) עם סיבת ההעברה והמועד הקודמים — מתנדב יכול ללקוח אותו מיד.

### מיון לפי גרסת הספרייה

לאחר **סיום פריסת כל תהליכי האתר** (ללא writers מהגרסה הקודמת), להריץ בסביבת השרת:

```sh
node scripts/migrate-corrections.mjs
node scripts/migrate-corrections.mjs --apply
```

הפקודה הראשונה היא dry-run בלבד. `versionSort` בתוצאה מציג כמה דיווחים צריכים השלמה/תיקון.
`--apply` שומר `libraryVersionSortKey` מספרי ו-`libraryVersionSortSchema`, ויוצר את אינדקסי המיון
בלי למחוק אינדקסים קיימים. הוא לא משנה את תוכן הדיווחים או את זמני העדכון שלהם. הרצה חוזרת בטוחה.
המפתח נכתב יחד עם הגרסה בקליטה ובעדכון דיווח ישן; עדכוני טיפול/פרסום אינם משנים את גרסת המקור.

לפני השלמת ה-migration הרשימה עדיין ממוינת נכון באמצעות חישוב בזמן הבקשה; אין השלמה אוטומטית
בהפעלת השרת. לאחר ההשלמה בדיקת הסמן משתמשת באינדקס, והרשימה משתמשת במפתח השמור ובאינדקסי
`schema → key → createdAt → _id` ו-`schema → state → key → createdAt → _id`.
סינונים סלקטיביים ועימוד עמוק עדיין עשויים לסרוק יותר פריטים; אין עוד חישוב גרסה לכל התור בכל עמוד.
ספירת `total` המדויקת נשארת שאילתת ספירה נפרדת.

לאחר rollback לקוד ישן וחזרה לגרסה החדשה יש להריץ שוב את שתי הפקודות: ה-migration מתקן גם
מפתח קיים שכבר אינו תואם לגרסה. אין להפעיל את מסלול המיון השמור מול writers ישנים שעדיין כותבים.

## 9. Rollback

- **קוד**: פריסת הגרסה הקודמת. כל השדות החדשים אופציונליים ומתעלמים מהם בקוד הישן (כולל `publish.prClosedAt`
  ו-`publish.absorbed`: דיווח שממתין לקליטה הוא `pr_opened`, והקוד הישן מעביר אותו לידני כשה-PR סגור, כמו קודם); `status` הישן
  מסונכרן, ולכן הדיווחים נראים כרגיל. אין לבצע migration הפוכה — **אין למחוק** דיווחים, החלטות, חבילות
  שינוי, ניסיונות פרסום או יומן (`CorrectionEvent`).
- **הקוד הישן מחזיר 500 כש-SMTP נכשל** — לקוח ישן יחזור וינסה; זו ההתנהגות שהייתה.
- **חזרה לגרסה החדשה אחרי rollback**: דיווחים שנקלטו בקוד הישן (בלי `state`) משודרגים בעצלות בפתיחה/לקיחה,
  או ב-`scripts/migrate-corrections.mjs --apply` (אידמפוטנטי).
- **עצירת אוטומציה בלי rollback**: מדף הניהול — השהיית השירות ו/או `publishMode=disabled`
  (אישורים נשמרים כ"אושר וממתין לפרסום" ויפורסמו כשיופעל מחדש).
- עצירת ה-worker: ביטול ה-cron. משימות פתוחות ממשיכות מאותו מקום בהרצה הבאה.

## 10. בדיקות

`npm test` מריץ גם את `src/lib/corrections/*.test.mjs`. בדיקות האינטגרציה (`*.int.test.mjs`) רצות מול
MongoDB אמיתי דרך `mongodb-memory-server-core` (הבינארי יורד בהרצה הראשונה ל-`~/.cache/mongodb-binaries`;
ברשת מסוננת: `NODE_EXTRA_CA_CERTS`). אם MongoDB לא זמין, הבדיקות מסומנות skip עם הסיבה — לא "עוברות".

מרשימת הדרישות מתחילה ב-`[T<n>]`.
