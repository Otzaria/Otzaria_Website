# מדריך למפתח — תוסף הכולל שירות חיצוני

## מה מגישים

השלימו תחילה את טופס העלאת התוסף הרגיל וסמנו ״דורש שירות חיצוני״. לאחר מכן עברו ל־`/plugins/<id>/service`. כל מתקין שמוצע למשתמשים חייב לעלות לחנות עצמה; קישור ל־Release אינו מחליף העלאת קובץ.

הגישו `.otzplugin` תקין לפי ה־SDK, ואת המתקינים למערכות הנתמכות. כל מתקין חייב לכלול **בדיוק את אותם בתים** של קובץ התוסף שהגשתם בנפרד. ציינו לכל מתקין מערכת, מעבד, מערכת מינימלית, פורט הזיהוי, נתיב התוסף בתוך המתקין וקישור ישיר לאותו קובץ ב־GitHub Release ציבורי. הגישו מאגרי מקור ציבוריים בפורמט `owner/repository`, עם commit מלא של 40 תווים לכל אחד. המקור צריך לכלול גם את קוד השירות, המתקין/המסיר והתוסף; ניתן להשתמש במאגרים נפרדים.

נדרש מקור שאפשר לסקור: הסתרה או חוסר בקוד הרלוונטי יכולים למנוע אישור. אל תכללו סיסמאות, מפתחות או מידע פרטי. טקסט בקוד שמנסה להורות לבודק נחשב ממצא.

בגרסה זו מתקבלים Windows ‏EXE/MSI/ZIP, macOS ‏DMG/PKG/ZIP, Linux ‏AppImage/DEB/RPM/ZIP ו־Android ‏APK. סיומת מותרת **אינה מבטיחה** שכל סוג אריזה ניתן לחילוץ: הבודק חייב לחלץ סטטית את התוסף המדויק באמצעות 7-Zip, בלי להפעיל את המתקין. מתקין רב־שכבתי או מוצפן שלא ניתן לבדוק כך ייעצר; אין מסלול ״הרץ כדי לבדוק״. בפרט, 7-Zip אינו פותח מתקיני **Inno Setup** וחבילות **WiX Burn**; השתמשו ב־NSIS, ב־MSI או ב־ZIP. צרפו עד שמונה קבצים, עד 256 MiB לקובץ, ותוסף עצמאי עד 50 MiB. לפרויקט מוגדר מספר גרסת שירות אחד לכל חבילת המערכות; מערכת שלא נתמכת לא נדרשת להיכלל.

## בנייה ב־GitHub Actions עם אישור בנייה — חובה

כל מתקין חייב להיבנות ב־GitHub Actions, על runner של GitHub, מתוך אחד המאגרים וה־commit שהגשתם, ולשאת אישור בנייה (build provenance). האישור מוכיח שהקובץ נבנה מהקוד הזה; הוא אינו מוכיח שהבנייה עצמה נקייה, ולכן קובצי ה־workflow וסקריפטי הבנייה נסקרים כמו שאר הקוד.

```yaml
permissions:
  contents: read
  id-token: write
  attestations: write

steps:
  - uses: actions/checkout@v4
  # ... בנייה, וחתימת קוד אם יש ...
  - uses: actions/attest-build-provenance@v2
    with:
      subject-path: dist/setup.exe
```

- חתימת קוד (Authenticode, notarization) מתבצעת **לפני** צעד האישור ובתוך אותו workflow; חתימה מאוחרת משנה את ה־hash.
- הקובץ שמועלה ל־Release ולחנות הוא בדיוק הקובץ שאושר.
- תלויות נעולות בקובצי lockfile. הורדת בינארי מוכן ואריזתו במקום בנייה נחשבת הסתרת קוד; כלי בנייה מותקנים דרך actions רשמיים.
- runner מסוג self-hosted אינו מתקבל.

לפני ההגשה ודאו את האישור בעצמכם:

```bash
gh attestation verify dist/setup.exe --repo OWNER/REPO
```

אישור חסר או שאינו תואם לקובץ, למאגר או ל־commit שהוגשו גורם לדחייה.

## התקנה מקומית והסרה

המתקין מתקין את השירות ואת הרכיבים הכלולים בו, מחלץ את התוסף לתיקייה זמנית ייחודית של המשתמש, ואז מפנה לאוצריא באמצעות:

```text
otzaria://plugin/install-local?path=<URL-encoded absolute path>
```

דוגמת PowerShell למתקין Windows, אחרי שהקובץ כבר חולץ:

```powershell
$PluginPath = 'C:\Users\Example\AppData\Local\Temp\MyService-unique\plugin.otzplugin'
if (-not (Test-Path -LiteralPath $PluginPath -PathType Leaf)) {
    throw 'The bundled plugin file is missing.'
}
$InstallUri = 'otzaria://plugin/install-local?path=' + [Uri]::EscapeDataString($PluginPath)
Start-Process -FilePath $InstallUri
```

הנתיב בדוגמה להמחשה; השתמשו במיקום החילוץ בפועל, לא בשם משתמש קבוע. הפניית URI אינה אישור שההתקנה הסתיימה: **אין למחוק מיד את קובץ ה־temp**. כשאותה גרסה כבר מותקנת, אוצריא שואלת את המשתמש אם לדרוס וקוראת את הקובץ שוב רק אחרי אישורו, כך שזמן ההמתנה אינו מוגבל. כדי לדעת מתי מותר למחוק, קראו את `plugin_install_results.jsonl` בשורש נתוני אוצריא (ב־Windows ‏`%APPDATA%\otzaria`; בהתקנה ניידת — תיקיית הנתונים שליד קובץ ההפעלה). כל שורה היא JSON עם `path`, ‏`pluginId`, ‏`version`, ‏`outcome` ו־`at`; חפשו שורה עם הנתיב שמסרתם ו־`at` מאוחר מזמן המסירה. ערכי `outcome`: `installed`, ‏`updated`, ‏`cancelled`, ‏`failed`, ‏`rejected_older`, ‏`rejected_incompatible`. הימצאות המפתח `pluginInstallResults` ב־`otzaria_capabilities.json` שבאותה תיקייה מעידה שגרסת אוצריא המותקנת כותבת יומן זה; בלעדיו השאירו את הקובץ למחיקה בהסרה.

אין להשתמש ב־`install?url=` להורדת עותק אחר. אוצריא דוחה בעצמה התקנה של גרסה ישנה מהמותקנת (`rejected_older`). על המתקין להסביר מה לעשות כשאוצריא אינה מותקנת או כשהמערכת אינה מאפשרת את פתיחת הקישור.

ב־macOS/Android/Linux יש להשתמש במנגנון הפתיחה והעברת הקובץ שהפלטפורמה ואוצריא תומכות בו. בדיקת מסירת קובץ מקומי בין יישומים נדרשת לכל פלטפורמה בנפרד; אין להניח ש־path של APK או תיקייה פרטית נגיש לאוצריא רק כי הוא עובד ב־Windows.

השירות חייב לספק הסרה רגילה של מערכת ההפעלה או מסיר כלול. הוראות ההסרה יופיעו בדף החנות. האחריות להפסקת השירות, הסרת רכיבים וניהול נתונים/מודלים בהסרה היא של המפתח. אין לצפות שאוצריא תסיר את השירות בעת הסרת התוסף.

## זיהוי שירות — חובה

לכל מערכת הגדירו פורט קבוע פנוי בתחום 1024–65535. הפורט ייחודי בחנות: הגשה עם פורט שכבר שייך לתוסף שירות אחר תיחסם. החזירו ב־GET ללא תופעות לוואי:

```http
GET http://127.0.0.1:18090/.well-known/otzaria-service
```

```json
{
  "protocolVersion": 1,
  "serviceId": "org.example.my-plugin",
  "serviceVersion": "1.0.0"
}
```

`serviceId` זהה ל־`manifest.id` של התוסף. `serviceVersion` הוא `X.Y.Z` ותואם לגרסה שהשירות מריץ, לא מספר מומצא כדי לעקוף את בדיקת התאימות. תשובה בגודל עד 4 KiB וב־`Content-Type: application/json`; אין redirect. אין צורך באימות לבדיקת מידע זו בלבד, שאינה חושפת פרטי משתמש. יש להקשיב ל־loopback, לא לכל ממשקי הרשת. **בדיקת Host חובה בכל נקודות השירות:** דחו בקשה שה־Host שלה אינו `127.0.0.1:<port>`, ‏`localhost:<port>` או `[::1]:<port>`. בלי זה אתר זדוני יכול לגשת לשירות דרך DNS rebinding, ו־CORS אינו מגן מכך.

לאתר החנות יש לאפשר CORS ל־`https://otzaria.org` (וכן לכתובת staging המדויקת בזמן פיתוח), עם `Vary: Origin` כשבוחרים Origin דינמית מתוך רשימה סגורה. אין צורך בעוגיות. דפדפנים עשויים לבקש הרשאת גישה מקומית; אין דרך להבטיח שהמשתמש יאשר אותה. CORS אינו אימות עבור פעולות השירות: קריאה/כתיבה/פקודות רגישות דורשות הגנות עצמאיות, ואין לחשוף ממשק כללי לא־מאומת להרצת פקודות או לגישה שרירותית לקבצים.

## תקשורת התוסף עם השירות

תוסף שפונה לשירות המקומי צריך את ההרשאה `network.localhost` (לא `network.access`), ‏`network.enabled: true`, ואת כתובת השירות ב־`network.allowlist`. כתובת מלאה עם פורט נועלת את התוסף לפורט שלכם. הקריאות עוברות דרך `network.fetchStream`; ‏`fetch()` ישיר מתוך התוסף נחסם. פרטים: פרק ״שירותים מקומיים (localhost)״ ב־`API_REFERENCE.md` של ה־SDK.

```json
"permissions": ["network.localhost"],
"network": { "enabled": true, "allowlist": ["http://127.0.0.1:18090"] }
```

## עדכונים ותאימות

ציינו טווח **גרסאות השירות שבהן התוסף עובד**, בנוסף ל־minAppVersion/maxAppVersion של אוצריא במניפסט. גרסאות השירות והתוסף נפרדות, בפורמט `X.Y.Z`. טווח כולל מינימום ומקסימום, או מינימום ללא תקרה. טווח ללא תקרה הוא הצהרת תאימות, לא ברירת מחדל שכדאי לסמן ללא בדיקה.

עדכון שירות כולל שוב את כל מתקיני חבילת הגרסה ואת התוסף שבתוכם. אפשר להתחיל בדיקת שירות אחת ל־21 יום. דחייה או ביטול לאחר תחילת הבדיקה אינם מאפסים את התקופה. תיקון מוקדם דורש חריגת מנהל. עדכון תוסף בלבד יכול להתבצע ללא מגבלת זמן זו, אך חייב גרסת תוסף חדשה ובדיקה; אין מעלים בו שוב את מתקיני השירות. לא משתמשים שוב במספר גרסה שכבר פורסם.

הורדת קוד חדש, self-update של השירות או סקריפטים מהרשת אסורים במסלול זה. הורדת מודל או נתונים מותרת רק כשהטעינה אינה מריצה קוד מהקובץ או מהמאגר. התקנת קוד שכבר כלול בחבילה שנבדקת מותרת. קיימת חזרה לגרסת שירות אחת קודמת, יחד עם התוסף הכלול בה; זו חזרה של ההפצה בחנות, לא שנמוך מרחוק של התקנות קיימות.

## דוגמת בקשת הגשה

הדפדפן בונה את הבקשה הזו; לרוב אין צורך לשלוח אותה ידנית. הנתיבים וה־hash של commit בדוגמה הם להחלפה בפרטי הפרויקט האמיתיים.

```json
{
  "kind": "service",
  "pluginVersion": "1.0.0",
  "pluginSize": 12345,
  "serviceVersion": "1.0.0",
  "serviceRange": {"min": "1.0.0", "max": "1.9.99"},
  "sources": [{"repository": "OWNER/REPO", "commit": "0123456789012345678901234567890123456789"}],
  "changeNotes": "הגשה ראשונה",
  "uninstall": "הסרה דרך אפליקציות מותקנות",
  "virusTotalConsent": false,
  "assets": [{
    "name": "setup.exe", "size": 12345678,
    "os": "windows", "arch": "x64", "minOs": "Windows 10",
    "port": 18090, "bundledPluginPath": "plugin.otzplugin",
    "releaseUrl": "https://github.com/OWNER/REPO/releases/download/v1.0.0/setup.exe"
  }]
}
```

לאחר יצירה מתקבל `_id` של ההגשה. העלו את הבתים ל־`assets/plugin` ו־`assets/native0` ואז בצעו `seal`. הגדלים חייבים להיות מדויקים; SHA-256 מחושב בשרת. אין שינוי קובץ שכבר נקלט. העלאה שנקטעה ניתנת לביטול והגשה מחדש לפני תחילת סקירה; ביטול מוחק את הקבצים שהועלו. יצירת הגשות והעלאות מוגבלות בקצב. הגשה שלא נבחרה בידי מנהל תוך 30 יום מבוטלת אוטומטית.

בעדכון תוסף בלבד: `kind="plugin"`; משמיטים `serviceVersion`, `assets` ו־`uninstall`; שאר פרטי התוסף, המקור וטווח התאימות נדרשים. השירות הנוכחי חייב להיות בטווח.

אם הופעל VirusTotal, נדרשת הסכמה מפורשת למסירת קובצי ההפצה ולשיתוף שלהם עם שותפי אבטחה; אין לשלוח סודות. דחייה מגיעה עם דוח בעברית, כולל פרטי קוד למפתח. זיהוי אנטי־וירוס עלול להיות שגוי; אין להריץ שוב ושוב את אותה הגשה בתקווה לקבל אישור אחר.
