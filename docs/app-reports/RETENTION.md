# ניקוי צרופות של דיווחים סגורים

הניקוי מופעל אוטומטית בכל שעה דרך `app-reports-sync.yml`, בתשתית ה־SSH שכבר משמשת לפריסת האתר. הוא מפעיל את קוד הגרסה הפרוסה ואת נתיב ה־cron המאומת בשרת עצמו. `CRON_SECRET` נקרא מקובצי הסביבה של Next בשרת, אינו מועבר ל־GitHub ואינו נכתב ללוג. דרושים סודות ה־SSH הקיימים, `CRON_SECRET` ו־`DICTA_LIBRARY_GITHUB_TOKEN`; בלי חיבור GitHub לא מתבצעת מחיקה. ה־workflow פועל רק במאגר הראשי. יש לפרוס את הקוד לפני ההפעלה הראשונה; הפעלה מול גרסה ישנה נכשלת באופן גלוי.

## מקור האמת ומועד הניקוי

`issueClosedAt` נשמר מתוך `closed_at` של תשובת GitHub API אמיתית, גם ב־webhook וגם בסנכרון המחזורי. `notifiedClosedAt`, מועד שליחה ומועד עדכון הרשומה אינם משמשים לקביעת זכאות. ה־cron הקיים משלים בהדרגה את מועדי הסגירה גם בדיווחים ישנים. 404/410, מצב לא מוכר, חסר במועד הסגירה או כשל תקשורת אינם הוכחה לסגירה.

לפני כל דיווח מועמד נשלפים שוב המצב ומועד הסגירה מ־GitHub. התשובה מתקבלת רק בעדכון אטומי מותנה מול המצב, הזמן ורוויזיית המצב שנקראו לפני ה־GET; תשובה ישנה אינה יכולה לדרוס webhook של פתיחה מחדש שהגיע בזמן הבקשה, גם כאשר מעברים חולקים אותה מילישנייה. הניקוי מתחיל רק לאחר לפחות 168 שעות ממועד הסגירה המאומת. פתיחה מחדש מבטלת את הזכאות ואת נעילת הניקוי; סגירה נוספת מתחילה מניין חדש. בדיקה מותנית נוספת במונגו לפני כל קובץ עוצרת ריצה שקיבלה בינתיים עדכון מצב. הדיווח חייב להיות משויך ל־issue, ולא להמתין לפרסום דיווח או תשובת מייל. טיוטות מקומיות כלל אינן נשמרות באוסף זה.

## אחסון, בטיחות וביצוע חלקי

כל ריצה מטפלת לכל היותר ב־10 דיווחים ו־40 קבצים, בלי לקרוא את תוכן הקבצים לזיכרון. אינדקסים מכסים את בחירת הדיווחים ואת חיפוש ההפניות. נעילה קצרה ועדכונים מותנים מונעים ביצוע כפול בין ריצות. לאחר כשל נרשם מועד ניסיון נוסף בעוד שעה, כך שדיווח פגום אינו חוסם אחרים.

נמחקים קובצי GridFS של תמונות, GIF, אבחון, לוגים, dump ותמונות מתשובות מייל. תגי הבעלות של הקבצים נבדקים; קובץ שאינו מזוהה כצרופת דיווח אינו נמחק. קובץ שחסר כבר אינו נחשב לכשל, וגם chunks שנותרו אחרי מחיקה חלקית מנוקים בהרצה חוזרת. לפני מחיקה נבדקות הפניות מכל דיווח אחר ומהעלאות ספרים פעילות. הפניה של הדיווח הסגור יכולה להימחק בזמן שהקובץ המשותף נשמר עבור הרשומה האחרת. במסלולי הקליטה הרגילים מוקצה תמיד מזהה קובץ חדש; אין מסלול של הוספת הפניה למזהה ישן במקביל לניקוי.

כל הפניה מוסרת רק אחרי מחיקה מוצלחת, קובץ שכבר חסר, או זיהוי של קובץ משותף שיש לשמר. כשל מאוחר משאיר את יתר ההפניות לניסיון הבא. מזהה הדיווח, סוגו, הסטטוס, מועדי היצירה והסגירה, הטקסט וקישורי ה־issue נשארים; אין מחיקת אישוז ב־GitHub. הצעות תיקון לספרים נשארות בהיסטוריית הטיפול ואינן חלק מאחסון הצרופות הזה.

`payloadCleanup` מתעד את מועד הניקוי, מועד הסגירה ששימש לו, סוגי המטענים, מספר ההפניות שהוסרו, קבצים משותפים, קבצים שכבר חסרו, שגיאה אחרונה ומועד ניסיון נוסף. `removedBytes` מונה רק בתים שנמחקו פיזית בהרצות שאושרו; קובץ משותף או שכבר חסר אינו מוסיף בתים. אחרי אובדן אישור כתיבה ייתכן שהסכום קטן מהנפח שפונה בפועל, ולכן אינו חשבונאות אחסון מדויקת. קבלת תמונה חדשה מאפסת את סימון ההשלמה כדי שהמטען החדש לא יישאר ללא ניקוי. סימון ההשלמה מותנה אטומית בכך שלא נותרה אף הפניה לצרופה; תמונה שנקלטת בזמן הסיום משאירה את הדיווח לניקוי בריצה הבאה, גם ברשומה ישנה וללא מיגרציה. יומן הטיפול ורשומת המעקב אינם נמחקים.

## בדיקות

`retention.int.test.mjs` משתמש ב־MongoDB ו־GridFS אמיתיים ובשעון נשלט: לפני הגבול, בדיוק בגבול ואחריו, פתיחה מחדש וסגירה נוספת, חסר במועד אמין, שיתוף קובץ עם דיווח פעיל, תורים פתוחים, כשל חלקי והרצה חוזרת, מחיקה שכבר בוצעה, מנות מוגבלות וריצות מקבילות. `cron-client.test.mjs` מפעיל שרת HTTP מקומי ומוודא שהמתזמן קורא לנתיב הנכון עם אימות ושהוא מדווח על כשל. בדיקות אלה אינן מפעילות את התזמון בייצור ואינן משנות נתוני משתמשים.
