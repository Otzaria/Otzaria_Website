# OCR מקומי (ספק `local`) — מדריך תפעול

מסמך זה מיועד למפעילי האתר. החוזה מול השירות: [`CONTRACT.md`](CONTRACT.md).

ספק ה-OCR השלישי בדיאלוג "OCR לספר שלם" ("מחשב מקומי"): האתר מכין PDF מתמונות העמודים, והעבודה
נכנסת לתור. שירות Windows ייעודי (`OtzariaTaskAgent`, ריפו נפרד) מושך אותה דרך `/api/worker/v1`,
מעבד אותה במחשב מקומי ומחזיר קובץ תוצאה. האתר קולט את התוצאה לעמודים בלי לדרוס עריכה אנושית.

```
מנהל ── POST /api/admin/books/ocr/start (method=local, requestId) ──▶ OcrJob: preparing → (PDF עמיד) → queued
                                                                         │
שירות OtzariaTaskAgent ── GET /api/worker/v1/jobs ── GET …/input ── POST …/status ── POST …/result
                                                                         │
                     קליטה: שמירה עמידה → נעילת hash → נעילת החלטה → החלה מותנית לכל עמוד → ack
                                                                         │
cron שעתי (/api/cron/ocr-local-cleanup): השלמת קליטות תקועות + מחיקת קבצים 24 שעות אחרי ה-ack
```

## 1. פריסה ראשונה — סדר הפעולות

1. **פריסה רגילה** (דחיפה ל-`master`, ראו `.github/workflows/deploy.yml`).
2. **מיד אחריה — מיגרציה** (בתיקיית האפליקציה ב-VPS, `MONGODB_URI` נקרא מ-`.env`):
   ```bash
   node scripts/migrate-ocr-local.mjs            # dry-run: מדפיס JSON של מה ייעשה, לא משנה דבר
   node scripts/migrate-ocr-local.mjs --apply    # מבצע
   ```
   המיגרציה ממלאת `active` בעבודות הקיימות, מחליפה את האינדקס הייחודי הישן (`{book:1}` עם
   `status:'running'`) ב-`book_active_unique` (`{book:1}` עם `active:true`), ויוצרת את `requestId_unique`
   ואת אינדקסי הרשימה והניקוי. היא אידמפוטנטית ואינה מוחקת רשומות. אם יש ספר עם יותר מעבודה פעילה
   אחת היא עוצרת עם דוח; `--fail-older-duplicates` מסמן את הישנות כ-`failed`.
   עד שהמיגרציה רצה, `activeFilter()` סובלני לרשומות בלי `active`, כך שהאתר ממשיך לעבוד.
3. **משתני סביבה** (סעיף 2) ב-`.env` של השרת, ואז `pm2 reload`.
4. **crontab** (סעיף 4).
5. **nginx** (סעיף 3).
6. **הגדרת השירות במחשב המקומי** עם אותו סוד ואותו `workerId` (ראו `docs/INSTALL.md` בריפו השירות).

MongoDB בייצור הוא standalone (אין טרנזקציות). כל ההגנות הן עדכון מותנה של מסמך יחיד וכתיבות
קריטיות עם `j:true`. כדי לאמת: `db.hello()` בלי `setName`.

## 2. משתני סביבה

| משתנה | חובה | ברירת מחדל | הסבר |
|---|---|---|---|
| `OCR_WORKER_SECRET` | כן | — | סוד ה-Bearer של העובד. לפחות 32 בתים: base64 או hex שמפוענחים ל-32 בתים ומעלה, או 43 תווי ASCII מודפסים ומעלה (אותו כלל כמו `SecretProvider` בשירות). |
| `OCR_WORKER_ID` | כן | — | מזהה העובד, `[A-Za-z0-9._-]{1,64}`. חייב להיות זהה ל-`Agent:WorkerId` בשירות. |
| `OCR_LOCAL_STORAGE_DIR` | לא | `<APP_DIR>/storage/ocr-local` | שורש קבצי העבודות (PDF קלט, תוצאות). פרטי, לא תחת `public/`. |
| `OCR_LOCAL_MAX_PAGES` | לא | `2000` | תקרת עמודים לעבודה. אפשר רק להנמיך (התקרה הקשיחה היא 2000, כמו בשירות). |
| `OCR_LOCAL_MAX_INPUT_BYTES` | לא | `536870912` (512MiB) | תקרת גודל ה-PDF. אפשר להנמיך; התקרה הקשיחה היא 1GiB. pdf-lib בונה את הקובץ בזיכרון של תהליך Next, ולכן ברירת המחדל שמרנית. |
| `CRON_SECRET` | כן (קיים) | — | משמש את ראוט הניקוי. |

- **סוד חסר או חלש** → כל `/api/worker/v1` מחזיר `403 {"error":"worker_api_disabled"}`. השירות מסווג
  זאת כבעיית תצורה: מחזיק את העבודות, מתריע למפעיל וממשיך לנסות. בדיאלוג, אפשרות "מחשב מקומי"
  מנוטרלת ("לא מוגדר בשרת") ובקשת start מחזירה `503 local_not_configured`.
- **"המחשב המעבד לא זמין"** בדיאלוג מוצג כשהעובד לא פנה לאתר יותר משתי דקות
  (`WORKER_ONLINE_WINDOW_MS` ב-`localJobState.js`). זו תצוגה בלבד; העבודה לעולם לא נכשלת בגלל זה.

### הפקת הסוד והזנתו

```bash
openssl rand -base64 32
```

- את הערך מזינים **ידנית** ל-`.env` בשרת (הקובץ מקושר ל-build בפריסה) ולקובץ הסוד של השירות
  (`Site:SecretFile`). לא דרך workflow, לא ב-`NEXT_PUBLIC_*` ולא ב-`next.config`. הסוד לעולם לא נרשם בלוג.
- **החלפת סוד:** מחליפים בשני הצדדים, ואחריהם `pm2 reload`. בחלון שבין ההחלפות השירות מקבל 401,
  מחזיק את העבודות והתוצאות ומנסה שוב (הוא קורא את קובץ הסוד מחדש כשהקובץ משתנה). שום דבר לא אובד.
- **לא מחליפים `OCR_WORKER_ID` כשיש עבודות פתוחות.** העבודות שייכות ל-workerId שבו נוצרו: עובד עם מזהה
  אחר לא יראה אותן, ותוצאות שלהן יקבלו 404. אם חייבים — קודם לסיים או לבטל את כל העבודות הפתוחות.
- **לא מפעילים שני מופעי שירות עם אותו workerId.** האתר מניח עובד יחיד לכל מזהה: שני מופעים יעבדו את
  אותן עבודות, ודיווחי המצב שלהם (`reportSeq`) יתחרו. השירות מגן על עצמו רק בתוך אותו מחשב (נעילת מופע).

## 3. nginx (ההגדרה אינה בריפו — נדרשת גישה ל-VPS)

```nginx
# תוצאה: עד 100MiB, והתשובה מגיעה רק אחרי החלה על כל העמודים (עד 10 דקות)
location ~ ^/api/worker/v1/jobs/[^/]+/result$ {
    client_max_body_size 110m;
    proxy_read_timeout   620s;
    proxy_send_timeout   620s;
    proxy_request_buffering off;   # אופציונלי: הזרמה ישירה לתהליך Next
    proxy_pass http://127.0.0.1:3000;
    # + כותרות ה-proxy הרגילות של האתר
}

# יצירת עבודה local: בניית ה-PDF (עד 2000 עמודים) לפני תשובת 202 (maxDuration 300)
location = /api/admin/books/ocr/start {
    proxy_read_timeout 620s;
    proxy_pass http://127.0.0.1:3000;
}
```

- בלי `client_max_body_size` מתאים, תוצאה גדולה תיכשל ב-413 **HTML** של nginx. השירות מפרש תשובת
  HTML כבעיית אימות/תצורה ומחזיק את המסירה עם התראה.
- בלי `proxy_read_timeout`, החלה ארוכה תקבל 504 אחרי 60 שניות. השירות ישלח שוב (הקליטה אידמפוטנטית
  וממשיכה מאותה נקודה), אבל כל שליחה מעלה את הקובץ כולו מחדש.
- גם ל-start: timeout של nginx בזמן הכנת PDF גדול לא יוצר כפילות (הדיאלוג חוזר עם אותו `requestId`),
  אבל עדיף שהבקשה תסתיים בפעם הראשונה.
- `proxyClientMaxBodySize: '500mb'` כבר מוגדר ב-`next.config.ts`, כך ש-Next עצמו לא מגביל.

## 4. cron

```cron
0 * * * * curl -fsS --max-time 600 -X POST -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron/ocr-local-cleanup
```

- `--max-time` חובה: השלב הראשון בריצה (`resumeStalledApplies`) משלים קליטות תקועות ואינו מוגבל בזמן.
  בלי תקרה, ריצה תקועה תצבור תהליכי curl.
- `ok:false` (השלמה שנכשלה, שגיאות ניקוי, דיסק לא מחובר) חוזר ב-**HTTP 200** כדי שהסיכום יירשם, ולכן
  `curl -f` נכשל רק על 401/500. להתראה גם על `ok:false` (cron שולח בדואר כל פלט; `"ok"` הוא המפתח הראשון,
  ו-`results[]` מכילים `"ok":true` משלהם — לכן העיגון ב-`^`):
  `out=$(curl -fsS --max-time 600 -X POST -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron/ocr-local-cleanup); echo "$out" | grep -q '^{"ok":true' || echo "ocr-local-cleanup: $out"`
- כל ריצה: (1) משלימה עבודות שנתקעו ב-`applying` (קריסת שרת באמצע קליטה, וה-lease של 5 דקות פג)
  מקובץ התוצאה השמור; (2) מוחקת קובצי קלט ותוצאה **24 שעות אחרי ה-ack** (`ackAt`), לא מסיום העיבוד;
  (3) מוחקת קובצי קלט יתומים של עבודות שנכשלו או בוטלו בלי ack; (4) מוחקת תוצאות שנדחו אחרי 30 יום,
  ותוצאות מתנגשות רק אחרי "סמן כנבדק" (סעיף 7); (5) מנקה קבצים זמניים.
- השלמה שנכשלה (קובץ תוצאה חסר/פגום וכו') לא סוגרת את העבודה: הקוד נרשם ב-`resumeErrorCode`
  (מוצג בדיאלוג כ"השלמת הקליטה מהקובץ השמור נכשלה"), והעבודה נדחית עד `resumeRetryAt`: שעה, שעתיים,
  4, 8, 16 שעות, ואחר כך פעם ביממה לעד. חריגה זמנית (Mongo/אחסון לא זמינים רגעית) נדחית רק ל-5 דקות
  (בפועל: הריצה הבאה), ומוכפלת עד יממה רק אחרי כשלונות חוזרים. עבודות שטרם נכשלו נבחרות לפניהן, כך
  שעבודות פגומות לא חוסמות את האחרות.
- **רשומות `OcrJob`, ה-ack והסיכום לא נמחקים לעולם.** השירות מפרש 404 ב-`GET /jobs/{id}` על עבודה שהוא מכיר (ונעלמה מהרשימה) כ-`site_missing`: רק אירוע, והעבודה נשמרת אצלו ואינה נסגרת.
- הניקוי מסרב לגעת בתיקיית עבודה שהיא symlink או junction.
- `/api/cron/*` מוחרג משער השבת.

## 5. אחסון וגיבוי

- `OCR_LOCAL_STORAGE_DIR` (ברירת מחדל `storage/ocr-local`) נשאר בין פריסות (`storage/` מוחרג ב-
  `scripts/deploy-web.sh` וב-tracing של `next.config.ts`) ו**יש לצרף אותו לגיבוי** יחד עם MongoDB.
  עבודה שב-DB מפנה לקובץ שאבד מקבלת 404 `input_unavailable` (העבודה נעצרת אצל השירות למפעיל).
- מבנה: `<root>/<jobId>/input-<sha256>.pdf`, `result-<sha256>.json`, `rejected-<sha256>.json`. הרשאות
  `0750` לתיקיות ו-`0640` לקבצים.
- נפח: PDF של ספר הוא בערך סכום גודלי ה-JPEG של העמודים (התמונות מוטמעות כמו שהן, בלי דחיסה מחדש),
  ועוד התוצאה (טקסט). הקבצים נמחקים יממה אחרי ה-ack.
- **מגבלה ידועה — נקודת עיגון ריקה:** אם `OCR_LOCAL_STORAGE_DIR` מצביע לדיסק שלא חובר, התיקייה נראית
  ריקה. הניקוי מסמן אז עבודות כ"נוקו", והן נבדקות שוב רק אחרי 30 יום. ודאו שהדיסק מחובר לפני הפעלת
  האפליקציה. כשהשורש עצמו חסר, קריאות הקלט והתוצאה מחזירות `503 storage_unavailable` עם `Retry-After`.

### שחזור מגיבוי

האחסון (`OCR_LOCAL_STORAGE_DIR`) ו-MongoDB הם **זוג**: הרשומות ב-DB מפנות לקבצים (`inputPath`, `resultPath`),
והקבצים נקראים רק דרך הרשומות. **אל תשחזרו רק צד אחד** (למשל DB בלי אחסון) ואל תערבבו גיבויים מזמנים
שונים, אלא אם אתם מוכנים לטפל בתוצאות המתוארות כאן. עדיף לגבות את שניהם באותה חלונית זמן.

סדר פעולות מומלץ:

1. עצרו את האפליקציה (`pm2 stop`) וכבו את השירות המקומי (`Stop-Service OtzariaTaskAgent`), כדי שלא ייכתב
   מצב חדש תוך כדי השחזור.
2. שחזרו את MongoDB ואת תיקיית האחסון. את תיקיית האחסון הנוכחית שמרו בצד (לא למחוק) עד שהכול נבדק.
   ודאו שהתיקייה משוחזרת לאותו `OCR_LOCAL_STORAGE_DIR` ושהכונן מחובר (סעיף 5, "נקודת עיגון ריקה").
3. הריצו `node scripts/migrate-ocr-local.mjs` (dry-run, בלי `--apply`) ובדקו שהדוח לא מציע שינוי. גיבוי ישן
   עלול לא לכלול את `book_active_unique`/`requestId_unique` ואת אינדקסי הרשימה והניקוי; אם הדוח מציע שינוי,
   הריצו `--apply` (אידמפוטנטי ואינו מוחק רשומות).
4. הפעילו את האתר (`pm2 start`/`reload`), ואז את השירות המקומי. השירות מיישב את עצמו מול האתר: מושך את רשימת
   העבודות, משווה עם הרשומות שלו, ושולח שוב תוצאות שהאתר לא אישר.
5. הריצו ידנית את ה-cron פעם אחת (סעיף "הפעלה ידנית של ה-cron" למטה) ובדקו ש-`ok:true` ושאין ב-`resumed.results`
   קודי שגיאה.

מה קורה כשהשחזור מחזיר מצב ישן (מצב ה-DB הוא שקובע; הקבצים תלויים בו):

| מצב אחרי השחזור | התנהגות בפועל | מה לעשות |
|---|---|---|
| עבודה ב-DB, קובץ הקלט חסר באחסון | `GET …/input` מחזיר `404 input_unavailable` (או `409 input_corrupt` אם הגודל לא תואם `inputBytes`). השירות מסווג זאת כדחייה קבועה ומעביר את העבודה ל-`needs_attention` (`input_unavailable`). אם שורש האחסון עצמו חסר: `503 storage_unavailable` (זמני, השירות מנסה שוב). | להחזיר את `<jobId>/input-<sha256>.pdf` מהגיבוי ואז `requeue` בשירות, או לבטל את העבודה באתר וליצור חדשה (ראו "ניסיון חוזר ידני"). קובץ הקלט אינו נבנה מחדש לאותה עבודה. |
| עבודה עם תוצאה נעולה (`resultSha256`) בלי ack, וקובץ התוצאה חסר | ה-cron (`resumeStalledApplies`) מחזיר `result_unavailable`, או `result_corrupt` אם ה-hash שונה, ולא משלים. העבודה נשארת פתוחה ונדחית לניסיון הבא (`resumeRetryAt`, עד יממה — סעיף 4). אם השירות עדיין מחזיק את התוצאה כלא-מאושרת, הוא שולח אותה שוב: הקליטה כותבת את הקובץ מחדש וממשיכה מאותה נקודה (החלה מותנית לכל עמוד, בלי כתיבה כפולה). | להמתין לשליחה החוזרת מהשירות; אם השירות כבר איבד את התוצאה — לבטל באתר וליצור עבודה חדשה. אם הקובץ הוחזר מהגיבוי ולא רוצים לחכות לניסיון הבא: `db.ocrjobs.updateOne({ _id: ObjectId("<jobId>") }, { $set: { resumeRetryAt: null } })` ואז הפעלה ידנית של ה-cron. |
| ack שאבד (ה-DB ישן מרגע האישור) | השירות שולח שוב את התוצאה. אם ב-DB יש ack לאותו hash → `200 already_received` עם ה-ack השמור, בלי לקרוא את הגוף לדיסק (רק מוודאים שה-hash תואם לכותרת). אם אין ack → הקליטה ממשיכה מהמצב ב-DB וה-ack יונפק מחדש. ה-DB מכיל גם את העמודים, ולכן העמודים ורשומת העבודה עקביים זה עם זה. | כלום; לאמת ב-`GET /jobs/<id>` ש-`closed:true` וה-ack קיים. |
| קבצים באחסון בלי רשומת עבודה (גיבוי DB ישן מהאחסון) | קבצים יתומים. **הניקוי עובד רק על רשומות `OcrJob`** ולכן לא נוגע בתיקיות שאין להן רשומה (ובתוך תיקיית עבודה קיימת אינו נוגע בשמות שאינם `input-/result-/rejected-<sha256>`). קבצים זמניים של כתיבה שנקטעה נמחקים אחרי 24 שעות. השירות מפרש עבודה שאינה קיימת באתר (404) כ-`site_missing`. | לבדוק שהעבודה אכן לא קיימת באתר, ואז למחוק את התיקייה ידנית. אל תמחקו תיקייה של עבודה שה-DB מכיר. |

- דיווחי מצב (`reportSeq`) של שירות ששוחזר לגיבוי ישן נבלעים עד שהמספר עובר את השמור באתר (סעיף 9).
- עבודות פעילות ב-DB המשוחזר נשארות חוסמות את הספר שלהן עד שיסתיימו או יבוטלו (מהדיאלוג, חוץ מ-`applying`).

### ניסיון חוזר ידני

| מצב העבודה | פעולה |
|---|---|
| `failed` / `cancelled` | העבודה סגורה, לא "מחיים" אותה. פעולה ידנית ש**משנה קלט** יוצרת `jobId` חדש (כלל המפרט): פותחים את הדיאלוג "OCR לספר שלם", בוחרים "מחשב מקומי" ומתחילים מחדש (נוצר `requestId` חדש). הספר כבר משוחרר, כי עבודה סגורה היא `active:false`. |
| `needs_attention` | הטיפול במחשב המקומי, לפי הסיבה (בדיאלוג: תווית עברית ומתחתיה ההודעה המקורית `<reason>: …`; הטבלה המלאה: `docs/operations.md` בריפו השירות, סעיף 3). אחרי הטיפול `requeue` בשירות (אותה עבודה, אותו קלט). אם הקלט שגוי/חסר באתר — מבטלים באתר (אם עדיין פעילה) ויוצרים עבודה חדשה. **`manifest_conflict` / `jobid_case_conflict`** (האתר שלח לעבודה נתונים קבועים אחרים — באג באתר): מבטלים באתר ויוצרים עבודה חדשה. ב-`manifest_conflict`, עבודה בלי תוצאה נסגרת אז אצל השירות כ-`cancelled`. ב-`jobid_case_conflict` השירות לא מקבל ביטול ממזהה באותיות אחרות, ולכן העבודה נשארת מוחנית אצלו לטיפול המפעיל (`docs/operations.md` בריפו השירות, סעיף 3). עבודה שכבר מחזיקה תוצאה (למשל הוחנתה קודם כ-`delivery_rejected`) שומרת אותה: אחרי בדיקה, `retry-delivery` שולח אותה שוב, והאתר עונה `ack:"cancelled"`. **עבודה מוחנית שהאתר כבר אישר את התוצאה שלה** (ה-ack נשמר אצל השירות): `retry-delivery` סוגר אותה מה-ack השמור בלי לשלוח שוב, ו-`requeue` נדחה. |
| פעילה (`queued`/`running`/…), יש לשנות קלט או הגדרות | מבטלים מהדיאלוג (לא ניתן ב-`applying`) ומתחילים עבודה חדשה. |
| `preparing` שנתקעה | הדיאלוג מציג "המשך הכנה" (אותו `requestId`, אותם פרמטרים). לא נוצרת עבודה כפולה. הכנה שנטושה לפני יותר מ-15 דקות נסגרת כ-`failed` (`prep_abandoned`) כשמגיעה בקשת start אחרת לספר. |
| תוצאה שנוצרה ולא נמסרה / נדחתה באתר | שליחה חוזרת נעשית **מצד השירות**: `& $exe retry-delivery <jobId>` (ראו `docs/operations.md` בריפו השירות, סעיף 5, "Manual retry / requeue"). `retry-delivery` **אינו עוקף** המתנה של השירות: אחרי `Retry-After` על `POST …/result` (עד שעה, ראו CONTRACT "`Retry-After`") או בזמן החזקת `delivery_auth`, התוצאה יוצאת רק כשההמתנה מסתיימת. `requeue <jobId> --discard-result` מעבד מחדש מההתחלה. התוצאה הישנה וה-checkpoint נשמרים בצד בשם `*.discarded-<utc>-<guid>`. |
| `applying` תקועה (קריסת שרת באמצע) | ה-cron השעתי משלים אותה (`resumeStalledApplies`, אחרי פקיעת ה-lease של 5 דקות) מהקובץ השמור, או שהשירות שולח שוב והאתר ממשיך מאותה נקודה. אי אפשר לבטל עבודה ב-`applying`. |

עבודה סגורה ללא ack מקבלת ניקוי של קובץ הקלט אחרי 24 שעות; עבודה חדשה לאותו ספר בונה PDF חדש.

הפעלה ידנית של ה-cron (משלים קליטות תקועות ומנקה קבצים; אידמפוטנטי):

```bash
curl -fsS --max-time 600 -X POST -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron/ocr-local-cleanup
```

התשובה כוללת `resumed` (מה הושלם, לכל עבודה `ok`/`code`) ו-`purge` (קבצים שנמחקו, שגיאות,
`storageMissing`). `ok:false` עם `storageMissing:true` פירושו שהדיסק לא מחובר. `resumed` כולל גם סיכום:
`succeeded` (applied/cancelled/already_closed), `contention` (apply_in_progress/not_stalled/not_found — צפוי,
לא תקלה), `failed` ו-`failedCodes` (קובץ חסר/פגום/לא תקין, job_closed, או חריגה זמנית); `failed>0` ⇒ `ok:false`.

## 6. שער שבת

`/api/worker/v1` **אינו מוחרג** משער השבת (`src/proxy.js`). בשבת ויו"ט כל קריאה מקבלת
`503 {"error":"shabbat"}` עם `Retry-After: 3600`. השירות מסווג זאת כתקלה זמנית, מכבד את
`Retry-After` ומנסה שוב בלי לאבד דבר: בשבת לא נמשכות עבודות חדשות, לא מתקבלים דיווחים ולא נמסרות
תוצאות. עיבוד שכבר רץ במחשב המקומי נשלט בצד השירות, מחוץ להיקף האתר.

מה זה אומר בפועל (שירות 1.0.142, HANDOVER 3.1 פריט 9):

- 3600 שניות הן בדיוק התקרה של השירות (`ErrorClassifier.MaxRetryAfter`, שעה). כל תשובת שבת עוצרת את הצד
  שקיבל אותה לשעה שלמה: רשימת העבודות, סבב הדיווחים (כל העבודות), ובמסירת תוצאה — **כל** המסירות. ההמתנה של
  המסירות נשמרת אצל השירות ושורדת הפעלה מחדש.
- לכן במוצאי שבת עשויה לעבור עד שעה מהתשובה האחרונה עד שהשירות פונה שוב לאתר. זה צפוי: לא צריך לעשות
  כלום, ו-`retry-delivery` לא מקצר את ההמתנה.
- אחרי 5 דקות בלי מענה לרשימת העבודות, השירות מעלה התראה `site_unreachable` (גם בזמן שהוא ממתין ל-`Retry-After`).
  בשבת זו התראה צפויה, והיא נעלמת מעצמה בתשובה הבאה לרשימה.

ההחלטה שלא להחריג היא
החלטה פתוחה (הלכתית ומדינית) הממתינה לאישור; ברירת המחדל שומרת על המדיניות הקיימת.

ב-dev, ה-proxy קורא ל-Hebcal ודורש `NEXTAUTH_SECRET` (בלעדיו הוא מפנה גם את `/api/worker`
להתחברות). בדיקות ידניות מריצים ביום חול.

## 7. ממשק הניהול

### מצבי עבודה

| מצב (`status`) | תווית בדיאלוג | מי מעביר | הערה |
|---|---|---|---|
| `preparing` | מכין קובץ לעיבוד | בקשת start | השרת בונה את ה-PDF. העובד לא רואה את העבודה עדיין. |
| `queued` | ממתין למחשב המקומי | start (PDF עמיד) / דיווח `queued` | השירות מדווח `queued` רק לעבודה שחזרה לתור אחרי שהתחילה (ניסיון חוזר, `requeue`). אז `workerState` הוא `queued`, והדיאלוג מציג "העבודה חזרה לתור במחשב המקומי" (`isRequeued` ב-`ocrJobView.js`). |
| `running` | בעיבוד | דיווח העובד | |
| `pausing` | בהשהיה | דיווח העובד | |
| `paused_runner` | מושהה — GitHub Runner פעיל | דיווח העובד | המחשב עסוק במשימת CI; העיבוד ימשיך מאותה נקודה. |
| `delivery_pending` | העיבוד הסתיים — ממתין למסירה | דיווח העובד | |
| `needs_attention` | דורש טיפול במחשב המעבד | דיווח העובד | `WorkerAttentionNotice` מציג תווית עברית לפי קוד הסיבה (`attentionReason` ב-`ocrJobView.js`, לכל 15 הקודים של השירות), הצעת פעולה ל-`manifest_conflict`/`jobid_case_conflict`/`delivery_rejected`, ומתחת את ההודעה המקורית (`<reason>: <טקסט קבוע>`) כטקסט רגיל. קוד שהאתר לא מכיר מוצג עם הקוד עצמו. הטיפול במחשב המקומי. |
| `applying` | קולט תוצאות לעמודים | קבלת תוצאה | לא ניתן לבטל. |
| `completed` | הסתיים | קליטה (`success`/`partial`) | `partial` בלי אף עמוד מוצלח נסגר כ-`failed` (`no_pages_succeeded`). |
| `failed` | נכשל | קליטה (`failed`) / כשל הכנה | |
| `cancelled` | בוטל | ביטול מנהל / מחיקת ספר / מיזוג | |

כל המצבים הפעילים (`preparing` עד `applying`) חוסמים עבודה נוספת לאותו ספר, בכל הספקים. עבודות
local לעולם לא מסומנות ככושלות ע"י `staleJobs` (שנשאר לספקי השרת בלבד).

### יצירה

- הדיאלוג שולח `requestId` (UUID) לכל לחיצה. ניסיון חוזר (רשת, 502/503/504, `409 preparing`) נשלח עם
  אותו מזהה, כך ש-timeout לא יוצר עבודה כפולה. אותו `requestId` עם פרמטרים אחרים → `409 request_conflict`.
- **"המשך הכנה":** אם הכנת ה-PDF נעצרה (תקלה זמנית בשרת → `500 preparation_retry`, או בקשה שנקטעה
  וה-lease של 10 דקות פג), הדיאלוג מציג כפתור "המשך הכנה" ששולח שוב את אותה בקשה (ה-`requestId`
  והפרמטרים נלקחים מהשרת). הכנה שה-lease שלה פג לפני יותר מ-15 דקות נסגרת כ-`failed`
  (`prep_abandoned`) כשמגיעה בקשת start אחרת לאותו ספר, כדי שלא תחסום אותו לעד.
  ניסיון שה-lease שלו פג ונלקח ע"י "המשך הכנה" אינו מכריע עוד (לא `queued` ולא `failed`) — רק בעל
  ה-lease הנוכחי; הישן מקבל את המצב הנוכחי (`409 preparing` / תשובת העבודה), וקובץ ה-PDF שבנה נמחק
  מיד או, אם העבודה עוד בהכנה, ע"י ה-cron אחרי סגירתה.
- פורמטי תמונה: JPEG מוטמע כמו שהוא, PNG מוטמע lossless. פורמט אחר (WebP, TIFF) דוחה את היצירה
  (`422`) עם רשימת העמודים.
- **300dpi — נקודת כיול:** ה-PDF מצהיר על כל תמונה כאילו נסרקה ב-300dpi (`DECLARED_DPI` ב-
  `localPdf.pure.js`). גודל העמוד ב-PDF נגזר מזה; צנרת ה-OCR במחשב המקומי מקבלת את הפיקסלים המקוריים.
  אם יתגלה שהצנרת מסיקה גודל אותיות מה-DPI המוצהר, זה המקום לכייל.
- במצב "דלג על עמודים ערוכים" נכנסים ל-PDF רק עמודים שאין בהם טקסט ברגע היצירה.

### ביטול

ביטול סוגר את העבודה מיד (`cancelled`, `active:false`) ומשחרר את הספר. השירות לומד על כך מהדיווח
הבא (`cancelRequested:true`), מהיעלמות העבודה מהרשימה ומ-`GET /jobs/{id}`. תוצאה שמגיעה אחר כך
נשמרת ומקבלת `ack:"cancelled"`, בלי לגעת בעמודים. אם הקליטה כבר החלה (`applying`): `409` "הקליטה כבר
החלה — לא ניתן לבטל". מחיקת ספר ומיזוג ספרים מבטלים קודם את עבודות ה-OCR שלו (ביטול מתועד, עם הסיבה).

### התנגשויות עם עריכה אנושית

כל עמוד מוחל רק אם `updatedAt` שלו זהה לזה שנרשם ביצירת העבודה. עמוד שנערך (או נתפס בידי עורך)
בינתיים לא נדרס: טקסט ה-OCR נשמר כהתנגשות (`OcrConflict`) להחלטת מנהל, והסיכום מציג "התנגשויות".

- בדיאלוג ה-OCR של הספר → רשימת ההתנגשויות הפתוחות **בספר כולו**, מכל העבודות המקומיות (גם אחרי
  עבודה חדשה מכל ספק), כל אחת עם העבודה שממנה הגיעה ועם טקסט ה-OCR לצד הטקסט הנוכחי ("הצג טקסטים").
- **"אמץ את טקסט ה-OCR"** (עם אישור): מחליף את הטקסט בעמוד, רק אם העמוד לא השתנה שוב מאז שנטען
  ברשימה; אחרת `409` "העמוד השתנה שוב — רעננו".
- **"שמור את הטקסט הקיים"**: סוגר את ההתנגשות בלי שינוי בעמוד.
- ההכרעה נתפסת לפני כתיבת העמוד: האימוץ מסמן את ההתנגשות "אימוץ ה-OCR בתהליך" (`applying`), ובזמן הזה
  "שמור את הקיים" (גם מחלון אחר) נדחה ב-`409 apply_in_progress`. אם הקליטה קרסה באמצע, אחרי 2 דקות
  הפעולה הבאה או טעינת הרשימה בודקת את העמוד: אם הטקסט נכתב, ההתנגשות נסגרת כ"אומץ". אחרת היא חוזרת
  להמתנה, ו-`updatedAt` של העמוד מוקדם באלפית שנייה כדי שכתיבה מאוחרת של הבקשה שקרסה לא תנחת — לכן
  אימוץ חוזר דורש רענון (`409` "העמוד השתנה שוב").
- שליחה חוזרת של אותה תוצאה לא יוצרת התנגשויות חדשות ולא מחזירה החלטה שהתקבלה.

### תוצאות שלא נקלטו

- **תוצאה מתנגשת** (hash אחר אחרי שתוצאה כבר ננעלה): נדחית ב-`409 result_conflict` ונשמרת כ-
  `rejected-<sha>.json` לבירור. הדיאלוג מציג אותה (וגם תוצאות כאלה שלא נבדקו מעבודות מקומיות קודמות,
  תחת "תוצאות מתנגשות מעבודות קודמות"); אחרי בדיקה לוחצים **"סמן כנבדק"**, ורק אז הניקוי מוחק את הקובץ.
  עד 20 התנגשויות פתוחות (שלא סומנו) לעבודה; מעבר לכך התנגשות חדשה נדחית באותו
  409 **בלי** שמירת הקובץ, עד שמסמנים התנגשויות כנבדקו. התוצאה לא אובדת: על 409 השירות מחנה את העבודה
  ב-`needs_attention` (`result_conflict`) ושומר את קובץ התוצאה אצלו (לא נמחק שם בלי ack). קריסה בין
  הרישום להעברה משאירה את הקובץ הרשום בשם `result-<sha>.json` עד שליחה חוזרת — הניקוי מטפל בו לפי הרשומה.
- **תוצאה שנדחתה** (JSON פגום, לא עברה ולידציה, או הגיעה אחרי שהעבודה נסגרה): מוצגת לבירור בלבד,
  והקובץ נמחק אחרי 30 יום (עד 20 דחיות שמורות לעבודה; מעבר לכך לא נשמר קובץ). השירות מחנה את
  העבודה ב-`needs_attention`, והטיפול במחשב המקומי.
- **קובץ `rejected-`/`result-` שאינו רשום בעבודה** (קריסה באמצע קליטה): הניקוי לא מוחק אותו לעולם.
  לבדוק ידנית ולמחוק ידנית.

## 8. בדיקה ידנית

### לקוח הדמה (בלי השירות)

```bash
# שרת dev עם המשתנים: MONGODB_URI, NEXTAUTH_SECRET, OCR_WORKER_SECRET, OCR_WORKER_ID (ואופציונלית OCR_LOCAL_STORAGE_DIR)
npm run dev
# צרו עבודה בדיאלוג "OCR לספר שלם" → "מחשב מקומי", ואז:
node scripts/ocr-local-fake-worker.mjs --base http://127.0.0.1:3000 --secret-file <קובץ-הסוד> --resend
#   --outcome success|partial|failed   --job <jobId>   --text "<קידומת>"
```

הסקריפט מושך את הרשימה, מוריד את ה-PDF ומאמת את ה-sha256, שולח `running` ו-`delivery_pending`,
שולח תוצאה עם טקסט דמה לכל עמוד, ועם `--resend` שולח אותה שוב. הפלט הצפוי: `ack: accepted` ואחריו
`ack (שליחה חוזרת): already_received`, ו-`GET /jobs/<id>` עם `closed:true` וה-ack. במסד, `updatedAt`
של העמודים לא משתנה בשליחה החוזרת. `reportSeq` של הסקריפט נגזר מהשעון: אל תריצו אותו ואת השירות
האמיתי על אותה עבודה (דיווחי השירות, שמתחילים מ-1, ייחשבו ישנים).

### השירות האמיתי מול האתר המקומי

בריפו השירות (`OtzariaTaskAgent`), עם `FakeHandler` (בלי GPU ובלי Runner):

```powershell
dotnet run --project src/OtzariaTaskAgent.Service -- --console --DataRoot $env:TEMP\otz-e2e --WorkerId <OCR_WORKER_ID> `
  --Site:BaseUrl http://127.0.0.1:3000 --Site:SecretFile <קובץ-הסוד> --Site:AllowInsecureLoopbackForTesting true `
  --Handlers:UseFake true --Runner:Mode None
```

(או הקובץ המוכן `publish\service\OtzariaTaskAgent.Service.exe` עם אותם ארגומנטים.) יוצרים עבודה
בדיאלוג ובודקים שהיא עוברת `queued` → עיבוד → `completed`, ושהעמודים קיבלו "טקסט מדומה לעמוד N".
`OtzariaTaskAgent.Service.exe status` עם אותם ארגומנטי תצורה (`--DataRoot`, `--WorkerId`, `--Site:BaseUrl`,
`--Site:SecretFile`) מציג את העבודה כ-`completed`.
`FakeHandler` מסיים מהר, ולכן ייתכן שלא יישלח אף דיווח מצב לפני המסירה. זה תקין.

## 9. מגבלות ידועות

- **נתוני פריסה ועזר נשמרים לצמיתות** (בוטלה המגבלה הקודמת "metadata לא נשמר"): לכל עמוד שיש לו טקסט,
  `layout` או `metadata` נכתבת רשומה באוסף `OcrPageResult` — ה-layout (שורות, תיבות, מילים, חלופות, מסגרות
  ומטריצת `toSource` לתמונת העמוד), נתוני העזר של העמוד והאזהרות. רשומה לכל עבודה (היסטוריה), והנוכחית היא זו
  שה-job וה-hash שלה שווים ל-`Page.lastOcrJobId`/`lastOcrResultSha256`. ה-`metadata` של הספר, `error` העליון
  ו-`layoutSummary` נשמרים ב-`OcrJob`. בניגוד לקובץ התוצאה הגולמי (נמחק 24 שעות אחרי ack), הרשומות נמחקות במחיקת
  הספר ובמיזוג ספרים (המיזוג יוצר עמודים חדשים בלי טקסט, ולכן הרשומות של העמודים הישנים נמחקות ואינן מועברות).
  אין באתר מחיקת עמוד בודד. רשומה של עמוד שאינו קיים (למשל עבודה שהתחילה ממש בזמן מחיקה) לעולם לא מוחזרת
  בנתיב הקריאה, כי הוא מאתר רשומה רק לפי עמוד קיים, ולכן היא רק נפח מת. ניקוי ידני, אם יידרש:
  `db.ocrpageresults.aggregate([{$lookup:{from:'pages',localField:'page',foreignField:'_id',as:'p'}},{$match:{p:{$size:0}}},{$project:{_id:1}}])`
  ואז `deleteMany` על המזהים שהתקבלו. layout פגום או גדול מ-1.125MiB לא נשמר (רק אזהרה), והטקסט נקלט כרגיל.
  פירוט: CONTRACT.md, "נתוני פריסה, אזהרות ונתוני עזר".
- **נפח `OcrPageResult` גדל עם כל הרצה ואינו מוגבל לעמוד:** רשומה לעמוד טיפוסי שוקלת כ-15–20KB (עמוד צפוף כ-60KB,
  ולכל היותר כ-1.2MB: layout או JSON שנדחה, ועוד metadata עד 64KiB). ספר של 2,000 עמודים מוסיף כ-40MB **בכל הרצת OCR**,
  וכל הרצה חוזרת על אותו ספר מוסיפה רשומות חדשות (אין ניקוי היסטוריה, ואין תקרה למספר הרשומות לעמוד). לעקוב אחרי
  הגודל (`db.ocrpageresults.stats()`), ואם יידרש, ניקוי רשומות ישנות שאינן הנוכחיות (job/hash שונים מ-`Page.lastOcrJobId`/
  `lastOcrResultSha256`, ושאין להן `OcrConflict` פתוחה) הוא החלטה נפרדת שעוד לא מומשה.
- **קריאה לממשק:** `GET /api/page-content/ocr-data?pageId=…` (או `bookPath`+`pageNumber`; `jobId` אופציונלי למנהלי
  ספרייה) — מוגן session, `private, no-store`, אותו כלל גישה כמו העורך. מחזיר את ה-layout הנוכחי ואת `image.matches`
  (האם התמונה הנוכחית של העמוד היא זו שנשלחה לעיבוד). כשהתמונה הוחלפה אחרי ה-OCR, הקואורדינטות אינן תקפות.
  דיוק המיפוי לתמונה (`toSource`) הוא ±1px (מתיחה פנימית של pdfium), ולא תת-פיקסלי. ה-sha256 של התמונה נשמר
  במטמון בזיכרון התהליך (עד 2,000 קבצים, LRU), לפי נתיב + גודל + mtime/ctime בננו-שניות + inode. קובץ שנכתב
  ב-5 השניות האחרונות לא נשמר במטמון. כל שינוי בקובץ פוסל את הרשומה, ולכן לא יוחזר "תואם" ישן. פירוט:
  `src/lib/ocr/imageInspectCache.pure.js`.
  `bookPath` עם `%` פגום מחזיר 400 "נתיב ספר לא תקין".
- **עבודה שבוטלה עם עמודים מוצלים:** העמודים לא נכתבים; הם מופיעים במסך ההתנגשויות עם הסיבה "העבודה בוטלה;
  טקסט שזוהה לפני הביטול", לאימוץ או דחייה בודדים (אין אימוץ גורף).
- **אינדקסים:** `scripts/migrate-ocr-local.mjs --apply` יוצר גם את אינדקסי `OcrPageResult` (אידמפוטנטי;
  autoIndex של האפליקציה יוצר אותם ממילא).
- **פורמט הטקסט הוא `export_otzaria`** של צנרת ה-OCR, והוא עשוי לכלול תגיות. הטקסט נשמר כמו שהוא;
  יש לבדוק ויזואלית בעורך.
- **נקודת עיגון ריקה** לאחסון — ראו סעיף 5.
- **אובדן ה-DB המקומי של השירות:** אחרי שחזור לגיבוי ישן, השירות עשוי לשלוח `reportSeq` נמוך מהשמור
  באתר. הדיווחים האלה נבלעים (רק "נראה לאחרונה" מתעדכן) עד שה-seq עובר את השמור. מסירת תוצאות לא
  מושפעת, ותוצאה שהאתר כבר קיבל מקבלת `already_received`.
- **שני עובדים עם אותו workerId** אינם נתמכים (סעיף 2).
- **זיכרון ביצירת PDF:** pdf-lib בונה את כל הקובץ בזיכרון של תהליך Next (עד `OCR_LOCAL_MAX_INPUT_BYTES`).
  אם יתגלה לחץ זיכרון, יש להעביר את הבנייה ל-worker thread.
- **התנגשות לפי `updatedAt` בלבד:** כל שינוי בעמוד אחרי יצירת העבודה, גם תפיסה בידי עורך בלי שינוי
  טקסט, נחשב התנגשות.
